# 00 · 深度分析（5W1H → 苏格拉底追问 → 双向钢人论证 → 重构）

> 版本: v0.1 | 更新: 2026-10-13 | 变更: 首次落档（任务规划V0.1.0）——「辩证统一」分析底稿，后续各节结论均由此推出

## 第一轮 · 发散（5W1H）

**What（事实）**
- 项目不是「从零开始」，而是一个已推进到后期的大型 monorepo：148 个 API 路由、56 个页面、68 个数据模型、1,081+118+4 个单测全绿、生产构建通过（11_基线指标 §11.2，本规划实测）。
- 已闭环的里程碑：认证/SSO、计费网关、账本、测评、套餐兑换、后台 RBAC/菜单/CMS/日志/报表（最近一个 `finalize-admin-ia-and-ops-gaps` 代码已落地、勾选滞后）。
- 需求中仍缺：功能开关运行时（§3.9）、限时优惠计费（§3.6）、收藏（§二）、顶栏搜索（§五.2 隐含）；暂停：微信扫码、在线支付；未做：生产部署与备份演练。
- 测试面的真空：e2e 不进 CI（ci.yml 头注释），e2e 两套配置并存，无覆盖率数字、无量级基线，契约测试非自动生成。
- 契约面的真空：错误码三处定义（web 运行时 22 码、shared 旧表冲突值、文档 §4 部分段），违反「唯一源」。
- 已证明 vs 仅声明：单测/tsc/lint/build/文档门禁 = 已证明（本规划跑过）；e2e 全绿、生产状态、子平台端口 = 仅声明。

**Why（深层原因）**
- 直接原因：前序里程碑以「后台治理」为主线（restructure + finalize 两轮），需求文档中的前台/计费类剩余条目被挂起。
- 根本原因：① 测试资产只在开发者本机（Windows、localhost:5435）运行，CI 无数据库，导致 e2e 结论无法在第三方复现；② 契约「先登记后实现」靠人工双源对齐，没有机器断言，所以出现了第三张冲突码表；③ 数据层的「当前行唯一」用了全列唯一索引替代部分索引（Prisma 不支持部分索引是诱因），与「价格历史」语义冲突。
- 只改表面的风险：直接做限时优惠而不修唯一约束 → 第二条价格行即 P2002；直接加功能开关而不定失败策略 → 开关表异常可放大为全站 403。

**Where / When（边界与时序）**
- 代码位置：契约 `packages/shared/src/**`；API `apps/web/app/api/v1/**`；领域 `apps/web/lib/features/**`；数据 `apps/web/prisma/**`；UI `apps/web/app/(site|admin)/**`、`components/**`。
- 时序：契约（S0）→ 迁移（S1）→ 依赖它们的切片（S2–S5）→ 文档收口（S7）；S8/S9 受外部裁决门控。
- 端口：Aidean 恒 3000（代码 5 处一致）；AideanBot 3333 仅以 OIDC 回调形式出现在本仓，且种子写成 3200（矛盾，TASK-008）。`PORT` 环境变量可覆盖 next 默认端口——由端口守卫脚本约束（TASK-007）。
- 不在范围：子平台仓库、支付/微信、生产以外的多环境、.example/history。

**Who（主体）**
- 决策人：用户（BLOCKING U-3/U-4/U-5/U-11 及 APPROVE 门禁）。
- 主 Agent（Hark）：契约语义、迁移 ADR、资金路径、全部 UI 设计实现、需求修订、生产部署（13 卡）。
- 外部 Agent：CRUD 端点、单测、e2e、CI/守卫脚本、种子、文档登记（33 卡）。
- 独立验证者：只看 diff + 运行结果，输出 PASS/FAIL/UNKNOWN（§11.4）。

**How（路径）**
- 读码确认现状 → 冻结六份契约（TS+zod，可编译、可自检）→ 切垂直切片 → 46 张原子任务卡（数据单一源脚本渲染，自动做所有权/环/并行/关键路径校验）→ 落盘 → 推送。
- 验证：每卡有可复制的验证命令与证据目录；切片验收由独立验证者执行；端口由守卫脚本断言。

**What if（前提变化）**
| 变化 | 后果 | 规划应对 |
|---|---|---|
| 配置缺失（DATABASE_URL/REDIS_URL） | ready 返回 503；e2e 明确失败而非超时 | TASK-003/005 把失败显性化 |
| 依赖服务不可用（上游模型平台） | 网关降级链；CI 中用 mock-upstream | TASK-006 注入 `AIDEAN_ENABLE_MOCK_UPSTREAM=1` |
| 接口字段变化 | 契约测试/类型检查失败 | 唯一源 + 生成式契约测试（TASK-001/004） |
| 端口被占用 | next 启动失败或漂移到其他端口 | 守卫脚本断言 3000；CI 固定 `-p 3000` |
| 执行者修改的文件与当前代码不一致 | 合并冲突/覆盖 | 所有权矩阵 + 资源锁串行边 + 「允许修改」白名单核对 |
| 前置任务未完成 | 依赖卡阻塞 | DAG 依赖 + 阻塞条件字段，禁止「先写再说」 |
| 测试通过但运行时失败 | 假完成 | CI 真库 e2e（S0）+ 带库集成测试（S1）+ 证据目录 |
| 运行成功但异常路径缺陷 | 隐患 | 契约② FAILURE_PATHS 覆盖表 + 每卡负向验收 |
| 原始前提不成立（如 TASK-010 证伪唯一约束缺陷） | S1 取消 | TASK-010 阻塞条件已写明：证伪则 011/012 取消、S4 改依赖 010 |
| 代码与任务描述冲突 | — | 以真实代码为准，停止并回报（每卡「阻塞条件」） |

## 第二轮 · 收敛与苏格拉底追问（逐个关键结论）

**结论 1：「项目主体已完成，剩余为少量需求缺口 + 测试与运维真空」**
1. 凭什么？148 路由/56 页面的存在 + 单测与构建实测全绿。2. 证据来自 HEAD 77c7952 真实代码。3. 是最新代码（pull = Already up to date）。4. 反证：e2e 未实测，可能有运行时缺陷。5. 是否把「路由存在」误判为「功能可用」？可能——所以 S0 把 e2e 搬进 CI 作为第一刀。6–8. 结论成立的前提是单测有效覆盖；若覆盖薄，结论需降级——S6 测覆盖率。9. 需要额外验证：CI 真库 e2e。10. 足以支撑「进入规划」，不足以支撑「可上线」。

**结论 2：「错误码存在冲突的多源」**
1. `packages/shared/src/types/index.ts:72-89` 与 `apps/web/app/api/v1/_lib/errors.ts:39-82` 逐值比对（selfcheck 脚本 mism=0 是针对冻结稿 vs web；shared 旧表与 web 的冲突值见 02 §2.2）。4. 反证：旧表 0 引用，「冲突」暂无运行时后果。5. 表面 vs 根因：根因是缺少唯一源断言，下一个开发者可能从 shared 导入旧表。10. 足以支撑 TASK-001 优先。

**结论 3：「model_prices 唯一约束会导致二次采集失败」**
1–2. 静态推理：`updateMany` 把当前行置为非当前 + 唯一索引 `(model_id,is_current)`。4. 反证：若采集从未对同一模型跑第二次、或历史行被其他逻辑删除，则未暴露；台账 v9.0 记「真实同步 458/0」——可能是首次同步。5. 可能误判？存在：PostgreSQL 唯一索引对 `false` 值同样生效，推理成立；但需真库确认。9. 必须复现 → TASK-010 放在 S1 首位，并写明「证伪则取消 011/012」。10. 不足以直接改 DDL，足以立复现卡。

**结论 4：「功能开关应 fail-open」**
4. 反证：fail-open 使「被关闭的计费功能」在 DB 抖动时被放开。7. 前提：开关表与主库同库，库挂时网关本身也无法计费。8. 若未来开关迁到 Redis/独立存储，前提失效。→ 记为 U-7 假设，DESIGN-001 写明可切换。

**结论 5：「AideanBot 使用 3333」**
4. 反证：种子 3200；Fleet 的 `FLEET_UI_PORT=3333` 双占（规范说明 :688）。7. 前提：用户口径与 e2e 为准。→ NON_BLOCKING U-6，TASK-008 按 3333，若用户改判按裁决值。

## 第三轮 · 双向钢人论证（关键方案）

**方案：第一刀做「步行骨架复验 + 契约守卫」，而非直接做缺失功能**
- 支持（最强）：没有真库 e2e，任何新功能的「完成」都只能自证；错误码唯一源是 S2–S5 所有新错误码（50010/50011/20003）的前提；骨架卡全部是小/中规模，风险低、解锁多（DAG 中 TASK-001 是 43 张卡的祖先、TASK-006 是 19 张卡的祖先）。
- 反对（最强）：用户要「重点实现核心功能」，第一刀不交付新业务功能，用户感知弱；CI 改造可能被网络/镜像问题拖住。
- 裁决：反对意见部分成立 → 将 S2（功能开关，MUST）与 S0 后半程交错（L1 起 014 即可启动），并把 S0 中可能卡住的 CI 改造（TASK-006）的阻塞条件写明；结论维持。

**方案：S1 先于 S4（先修约束再做优惠）**
- 支持：不修则优惠行无法插入（与 isCurrent=false 的历史行冲突），这是硬前置。
- 反对：可以把优惠存到新表绕开。→ 反驳：新表 = 「提前设计表」且与 `PriceSource.PROMOTION` 既有建模（schema 注释明言限时优惠=PROMOTION 行）重复，违反单一事实来源。结论维持。

**方案：开关后台复用 `admin.configs.*` 而非新权限域**
- 支持：S7 先例；免 `seed-rbac` 重跑（CHANGELOG S4 记录的 db:seed 陷阱）。
- 反对：粒度变粗——能改站点配置者即能关网关。→ 记为 U-14 NON_BLOCKING，若用户要求细分，升 opus 复核 RBAC 后加域。

**方案：UI 全部由主 Agent 完成**
- 支持：用户明确要求；UI 需要设计判断（契约⑥五态、主题对比度）。
- 反对：UI 卡集中在主 Agent → 主 Agent 成为瓶颈（018/023/029/034 合计 44h）。→ 部分成立：DAG 中 018 与 023 可并行但同属主 Agent，实际会串行；关键路径计算已按工时计入，仍以 029（S4 UI）在关键路径上。接受该代价，作为风险 R-05 登记。
