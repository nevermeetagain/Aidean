# 经验教训

> 版本: v1.2 | 更新: 2026-09-19 | 变更: 事故 1 追加第 6 次复现——哨兵校验通过后仍可消失，dev 启动失败首选 `pnpm install --force --frozen-lockfile` 轻量恢复。
> 前次（v1.1 | 2026-09-18）：事故 1 追加第 4/5 次复现——构建成功亦可触发、恢复仅需根 `pnpm install --force --frozen-lockfile`（无需 Remove-Item）

> 定位：本文档收录**跨会话可复现的环境事故**根因与预防规则，口径以实际验证过的恢复流程为准。
> 适用范围：Windows 本机开发与本地 standalone 生产验证环境（非容器）。

## 一、事故台账（按危害排序）

### 1. .pnpm next 目录整体消失（已发生 7 次，两种触发形态）

- **现象**：`node_modules/.pnpm/next@*/node_modules/next/dist` 目录整体消失 → `Command next not found`、`jest-worker processChild missing`，或 dev 崩溃 `Cannot find module 'next/dist/pages/_app'`。
- **两种触发形态**：
  - 形态 A（第 1–3 次）：`next build` 被强制终止（或挂在 WorkerError 后被杀）后触发；根因为 Windows 文件锁未释放时强行删除/覆盖正在运行的 next 包目录，pnpm 硬链接存储被截断。
  - 形态 B（第 4–5 次，2026-09-18）：**构建完全成功**、未经任何强杀后同样发生，且同会话内复现两次；外部删除者仍未定位（与《验收复核》§2.3 留观项同源）。结论：不能把「构建成功」当作 dist 完好的前提。
- **第 6 次（2026-09-19，形态 B）**：置信度收口轮会话内，哨兵四文件校验**通过后数秒**、未执行任何构建的情况下启动 dev 即报 `Cannot find module 'next/dist/pages/_app'`；复核 `dist/pages/` 整目录已消失。按本条流程根 `pnpm install --force --frozen-lockfile` **7.5s 恢复**（全包 store 复用），随后 dev 正常。教训强化：哨兵校验通过≠此后不消失（外部删除者仍未定位，可在校验与启动的间隙触发）；dev 启动报 _app MODULE_NOT_FOUND 时不必排查代码，直接走恢复流程第 1 步。
- **第 7 次（2026-09-19，形态 A）**：同一会话内，哨兵四文件校验**通过**→`next build` **成功（EXIT=0）**→紧接启动 dev 即 MODULE_NOT_FOUND，四哨兵文件**全部消失**（时间线 <1 分钟）。`pnpm install --force --frozen-lockfile` **5.6s 恢复**。两次间隔实证：删除窗口横跨「构建前后/启动前后」全程，逐次哨兵校验只能发现、不能预防。
- **恢复**（两形态均已验证有效）：
  1. 先试最轻量路径（形态 B 实测约 5 秒，全部包从 store 复用）：仓库根 `pnpm install --force --frozen-lockfile`；
  2. 仅当 install 后哨兵文件仍缺失时，才 `Remove-Item` 损坏的 `.pnpm/next@<hash>` 目录后重试（形态 A 旧路径，约 1 分钟）；
  3. 校验 4 个哨兵文件存在：`dist/bin/next`（无 .js 扩展名）、`dist/pages/_app.js`、`dist/server/next-server.js`、`dist/compiled/jest-worker/processChild.js`。
- **预防**：杀构建/杀 node 前先确认无文件锁；每次构建（无论成败）后、重启 dev 前跑哨兵文件校验；dist 缺失属环境层故障，禁止为此改依赖版本或删整个 store。

### 2. 孤儿 standalone 进程锁死 .next → next build 永久挂起

- **现象**：`next build` 无限挂起（无 BUILD_ID、无进度输出）。
- **根因**：后台任务的 StopCommand 不一定杀死 node 子进程——孤儿 `node .../standalone/apps/web/server.js` 存活并占用 :3000 与 .next 文件锁。
- **预防（构建前必检）**：`Get-CimInstance Win32_Process` 过滤 CommandLine 含 `standalone\apps\web\server.js` 的 node.exe，存在则先 `Stop-Process -Force`。
- **关联**：先修本条再谈构建，可显著降低事故 1 的触发概率。

### 3. standalone 产物不含 static/public → 页面渲染但完全无交互

- **现象**：页面 SSR HTML 正常、无 console 报错（除 chunk 404），但点击/切换全部无响应——hydration 永不发生。
- **根因**：`output: "standalone"` 不包含 `.next/static` 与 `public`。
- **预防（每次 build 后必做）**：
  1. `Copy-Item apps\web\.next\static → .next\standalone\apps\web\.next\static`；
  2. `Copy-Item apps\web\public → .next\standalone\apps\web\public`；
  3. 再启动 server，缺一步即死页。

### 4. UI 位置规范回退争议（v2.3 左右位镜像）

- **现象**：工具栏横向布局在迭代中被镜像（筛选/版本、排序/视图的左右位置对调），用户要求恢复原版式。
- **根因**：布局重心从"功能聚合"（筛选+筛选）调整为"对齐美观"时，未对照前一版本截图基线。
- **预防**：涉及工具栏行内顺序的改动，PR 描述必须附改动前/后对照；以《界面交互文档》工具栏节为唯一口径。

## 二、流程性教训

1. **验证矩阵**：vitest（esbuild）不做类型检查、mock 可掩盖 Prisma schema 问题——提交前必须过 `tsc --noEmit` + `next build` + e2e 冒烟。
2. **Windows 并发编辑**：对同一文件的多路并行编辑会相互覆盖——同一文件的多处修改必须串行。
3. **构建挂起的排查顺序**：先查孤儿进程（事故 2）→ 再查文件锁 → 最后才考虑杀构建（杀之前预读事故 1 恢复流程）。
4. **本地 tsc 失败禁止提交**：CI 第一道门禁即文档检查 + tsc，本地不绿远程必红。
