# 开发流程

> 版本: v1.0 | 更新: 2026-08-26 | 变更: 首次落档——确立六步开发循环、四级层级与六字段字典为本项目一切功能性变更的工作规范（来源 change-id: `establish-dev-workflow`）

本文档是项目级「怎么做事」的唯一权威真源，回答三个问题：一个功能性变更经过哪些步骤（§一 六步循环）、任务书写成什么格式（§二 四级层级）、每个最小单元要补齐哪些原子信息（§三 六字段字典）。新里程碑从 [`_template/`](../specs/_template/spec.md) 起步，现行范本见 [`docs/specs/establish-dev-workflow/`](../specs/establish-dev-workflow/spec.md)。

## 一、六步开发循环

一切功能性变更依序执行、逐步放行；任一步未达通过条件，不得进入下一步：

**PLAN 规划** —— 做什么：对新增想法/问题/里程碑开展深度推理澄清，界定目标、边界与待确认分叉点；无法自决的分叉向决策人收敛追问，直至置信度达标。产物：经确认的目标、边界与分叉决议记录。通过条件：目标明确、范围收敛、关键分叉均有裁决。

**SPEC 规格** —— 做什么：在 `docs/specs/<动词短语-change-id>/` 目录写入 spec.md / tasks.md / checklist.md 三件套，全部按 §二 四级层级与 §三 六字段格式书写，语言与决策人一致。产物：完整的规格三件套。通过条件：每个子任务的必填信息齐备且验收标准可证伪。

**APPROVE 批准** —— 做什么：将三件套提交决策人审批；被拒则仅凭决策人反馈或澄清结果修订重提，不得擅自开工。产物：获得批准的三件套。通过条件：决策人明确批准；这是实施前的强制门禁。

**IMPLEMENT 实施** —— 做什么：以 tasks.md 为执行看板，按声明的依赖顺序推进各子任务；无依赖项可并行，每完成一项即勾选对应复选框。产物：变更后的代码/目录与 tasks.md 的逐项勾选痕迹。通过条件：全部子任务完成且实施未偏离已批 scope。

**VERIFY 核验** —— 做什么：按 checklist.md 分组逐检查点取证（命令输出/自动化测试/描述式断言）；任一失败即在 tasks.md 追加 `Fix:` 任务（引用检查点编号），修复后重验形成闭环。产物：全勾的 checklist 及取证记录。通过条件：所有分组全部通过，门禁命令退出码为 0。

**CLOSE 归档** —— 做什么：产出最终摘要回执；spec 目录永久保留不得删除；若涉及目录结构变更，同步回写《目录结构文档》（铁律 6）。产物：收尾摘要与同步后的权威文档。通过条件：回执产出，且相关文档与实际状态一致。

## 二、四级层级（任务书书写格式）

tasks.md 一律按以下四级组织，且每级以标题行声明本级职责：

| 级 | Markdown 载体 | 本级职责 |
|---|---|---|
| **L1 阶段** | `## …`（轨道 / Phase） | 声明该组目标、前置条件、交付物 |
| **L2 任务** | `### Task x.y 名称` | 一个可独立验收的功能面；标注【依赖】【产出】 |
| **L3 子任务** | `#### SubTask x.y.z 名称` | 最小可执行单元；字段完备即合法 |
| **L4 字段** | 子任务下有序列表项 `- 【字段】: 内容` | 最小原子信息：目标/范围/验收/验证命令/产出/依赖 |

两条执行纪律：① **合法性**——任一 L3 缺失任一必填字段即为非法任务，实施者停止执行并先要求补齐；② **复选框规则**——L2 勾选 = 其全部 L3 完成且 checklist 对应检查点通过，L3 自身完成即时勾选。

## 三、六字段字典（L3 强制内联）

| 字段 | 必填 | 内容要求 |
|---|---|---|
| 【目标】 | ✅ 必填 | 一句话说明做什么与为什么 |
| 【范围】 | ✅ 必填 | 精确到 glob 的目录/文件涉及面（新建/修改/移动须注明动作类型） |
| 【验收】 | ✅ 必填 | 可证伪标准；优先写成确切命令，纯 UI/视觉允许描述式断言 |
| 【验证命令】 | ⭕ 可选 | PowerShell 兼容的可执行取证命令（有则必填内容） |
| 【产出】 | ⭕ 可选 | 完成后新增/变化的可见工件 |
| 【依赖】 | ⭕ 可选 | 前置 SubTask/Task 编号；无依赖可省略 |

## 四、增量展开规则

- **新里程碑 = 新 change-id**：凡超出当前 change-id 范围的新里程碑，须新建 `docs/specs/<动词短语-change-id>/` 三件套（从 [`_template/`](../specs/_template/tasks.md) 起步），并且该 spec 的影响面章节 MUST 显式声明继承本流程的四层级与六字段规范；其 checklist SHOULD 至少包含一条与本 workflow 的回归联动检查（如全局构建门禁）。
- **粒度递减策略**：近期启动的能力（成熟度对应既有路线图 Phase 0–2）全量细化到 L3×L4 六字段；中期能力展开到模块级 L2 并附关键 L3，其余细节在该模块开工时以新 change-id 补齐；远期愿景仅保留 L2 级条目，禁止提前穷举实现细节。远景条目开工即立项，立项即继承本流程，不做例外。

## 五、全局约束（三条，凌驾于局部便利之上）

1. **技术栈偏离须先 ADR**：任何偏离技术栈锁定（ADR-0001：Next.js 15 + PostgreSQL 16 + Redis + Prisma + Tailwind 4）的变更，必须先提交新 ADR 并通过评审，方可进入 IMPLEMENT；评审未过即冻结原方案。
2. **公开接口变更契约先行**：凡影响公开接口响应（请求/响应结构、错误码语义）的变更，必须先更新 packages/shared 的 Zod Schema 并使对应测试通过，再改动端点实现——契约是消费方与提供方的共同前提，实现永远落后契约半步。
3. **敏感字段一票否决回滚**：成本敏感字段 `markup_rate` / `token_multiplier`（计费口径见[术语表 · 统一计费网关](术语表.md#六统一计费网关)）一旦出现在任何面向用户的输出（API 响应体、页面渲染、客户端日志、快照等），无论是否恶意、无论影响多大，一律一票否决、立即回滚；此类信息仅允许 admin 视角的序列化路径携带。
