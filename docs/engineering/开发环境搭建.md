## 二、本地启动（开发）

```bash
# 1. 安装依赖
pnpm install

# 2. 准备环境变量
cp .env.example .env.local      # 填入 DATABASE_URL / REDIS_URL / JWT_SECRET 等

# 3. 数据库
pnpm prisma generate            # 生成 Client
pnpm prisma db push             # 同步 schema 到本地库（或 db migrate dev）
pnpm prisma db seed             # 可选：写入初始/演示数据

# 4. 启动开发服务
TURBOPACK=1 pnpm dev            # 默认 http://localhost:3000
# ⚠️ Node.js v24 上 webpack 初始化挂起（"Starting..." 后无限等待），
# 须 TURBOPACK=1（turbopack Ready ~900ms）。next build 同理须 TURBOPACK=1。
```

### 2.1 后台起服与端口释放（Windows 实测）

dev server 需脱离当前终端持续运行时，用 `Start-Process` 起服并把日志落盘（`*.log` 已在 `.gitignore`）：

```powershell
Start-Process -FilePath 'cmd.exe' `
  -ArgumentList '/c','set TURBOPACK=1&& pnpm dev' `
  -WorkingDirectory '<repo-root>' `
  -RedirectStandardOutput '<repo-root>\dev-3000.out.log' `
  -RedirectStandardError  '<repo-root>\dev-3000.err.log' `
  -WindowStyle Hidden
```

端口被历史进程占用（`GET /` 打不开或打开的是旧进程）时，**先确权再释放**：

```powershell
# 1) 查监听者
Get-NetTCPConnection -LocalPort 3000 -State Listen | Select-Object LocalAddress,LocalPort,OwningProcess
# 2) 确认归属（务必核对 CommandLine 是否为本仓库路径）
(Get-CimInstance Win32_Process -Filter "ProcessId=<PID>").CommandLine
# 3) 连子树释放：pnpm/turbo → node next dev → start-server.js 三层
taskkill /PID <父PID> /T /F
```

> 实测陷阱（2026-09-23）：启动它的终端已关闭，`next dev -p 3000` 子树仍以**孤儿态**占着 3000（当时占用者 PID 41308 = `next/dist/server/lib/start-server.js`，父进程 1968 = `next dev`，父之 41304 已消亡）。故一律按 PID 树 `taskkill /T` 处理；释放后须自查 `Get-NetTCPConnection -LocalPort 3000` 为空、且新进程为唯一监听者。

## 三、Docker 部署（生产，Ubuntu）

基础服务（pg + redis + nginx）与 Web 应用分别编排，支持一键或分开启动、完全解耦。

```bash
# 一键启动全部（含基础服务 + web）
docker compose -f docker-compose.base.yml -f docker-compose.web.yml up -d

# 仅基础服务
docker compose -f docker-compose.base.yml up -d
```

- Web 镜像：多阶段构建（`Dockerfile`），`entrypoint.sh` 执行 `prisma migrate deploy` + `node server.js`。
- Nginx：反向代理 `/` → `app:3000`，443 配置 SSL；RagFlow 等子平台走独立 `server` 块。
- 国内镜像：构建与拉取均优先国内源；HF / pip 镜像在 RagFlow 相关服务中配置。

## 五、常见问题

- **pnpm store 空壳（`Cannot find module '.../next/dist/compiled/jest-worker/processChild.js'`、`Cannot find module 'source-map-js'` 等 build/PostCSS 报缺文件）**：pnpm 的内容寻址 store（`pnpm store path`，本机 `E:\.pnpm-store\v3`）中某包条目**整树变空壳**——目录与符号链接都在，但包体 `dist/` 全缺（如 next@15.0.0 条目实测 8.0K、仅 25 个节点；正常 113M）。常见诱因是 `node_modules` 被外部复制/压缩/清理后硬链接失效，store 里对应的文件被截断。**诊断**：`pnpm store status` 会列出被篡改条目（末行提示 `refetch the modified packages`），或对可疑包直接 `ls node_modules/.pnpm/<pkg@ver>*/node_modules/<pkg>/dist` 判空。**修复**：清 node_modules 后重装可让好条目重链接、坏条目重新 fetch（本机 2026-10-08 实测：28+ 包空壳，clean rebuild 后 `pnpm store status` → `Packages in the store are untouched`，`next build` exit 0）：
  ```powershell
  # 1) 清 node_modules（保留 lockfile）
  rm -rf node_modules apps/web/node_modules packages/*/node_modules
  # 2) 重装（不加 --frozen-lockfile，强制对坏条目重新 fetch 入库）
  pnpm install
  # 3) 复核 store 完整性
  pnpm store status     # 期望: Packages in the store are untouched
  ```
  仅单包损坏时可退一步 `pnpm install --force`（同上加 `--frozen-lockfile` 仍会 re-fetch 被篡改包）。这是**本机环境问题，不改代码**，但会在 `next build`/vitest 首跑时以"缺文件"形式暴露，勿误判为代码回归。已登记台账 §7.27。
- **`prisma` 命令超时**：确认 `DATABASE_URL` 可达；开发环境优先 `db push` 而非 `migrate`。
- **构建卡在启动**：`next build` 在资源受限机器可能偏慢，属环境项，非代码回归。
- **国内拉取慢**：统一配置 Docker / npm / Prisma / HF 国内镜像源。
- **`pnpm gates` 的 `prisma-check` 假红（配置只写在 `.env.local` 时）**：门禁自身能从 `apps/web/.env.local` 解析出 `DATABASE_URL` 并打印来源，但**未把该值注入子进程环境**；而 Prisma CLI 默认只读 `apps/web/.env`、`apps/web/prisma/.env`（**不读 `.env.local`**）→ `prisma validate` 报 `P1012 Environment variable not found: DATABASE_URL`，`pnpm gates` 退出码 1。当前规避（先导出再跑门禁）：
  ```powershell
  $line = Get-Content 'apps\web\.env.local' -Encoding UTF8 | Where-Object { $_ -match '^DATABASE_URL' }
  $env:DATABASE_URL = ($line -split '=',2)[1].Trim().Trim('"')
  pnpm gates        # 实测 5/5 PASS / EXIT=0
  ```
  同一根因覆盖所有 `pnpm prisma ...` 脚本：本地跑 `db:push` / `db:seed` 前须同样导出，或补一份 `apps/web/.env`（已被 `.gitignore`）。已登记台账 **#44**（《[未完成事项目录](../plans/未完成事项目录.md)》§7.5）。
- **启动日志 `Invalid next.config.mjs options detected: Unrecognized key(s) in object: 'optimizePackageImports'`**：`apps/web/next.config.mjs:7` 把 `optimizePackageImports` 放在**顶层**，而 next@15.0.0 只认 [`experimental.optimizePackageImports`](https://nextjs.org/docs/15/app/api-reference/config/next-config-js/optimizePackageImports)（官方 v15 文档口径）——**有告警即代表该配置被丢弃（静默 no-op，非纯噪声）**。影响面：`zustand` 未获 barrel 优化；`lucide-react` 本就在 Next 15 默认优化清单内，其配置项冗余。属功能性配置变更，须按六步循环立项后修，本轮未改。已登记台账 **#45**。

## 六、代码检索规范

- **grep 检索时排除构建产物**：`apps/web/.next/` 会在 `next build` 后生成大量编译文件，干扰全文搜索。统一加 `--exclude-dir=.next`：
  ```bash
  grep -rn --exclude-dir=.next --exclude-dir=node_modules "关键词" apps/web/
  ```
- **rg（ripgrep）默认排除 .git 和 node_modules**，但仍需显式排除 `.next`：
  ```bash
  rg "关键词" apps/web/ -g '!.next'
  ```
