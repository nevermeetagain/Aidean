## 五、性能验收口径（M-PERF，2026-09-03）

### 5.1 测量口径

- **一律以 prod 为准**：`pnpm --filter web exec next build && next start` 后测量；`next dev` 的按需编译延迟不计入体验评估（dev 下编译占首击延迟大头，非生产形态）。
- 详情页数据新鲜度：ISR `revalidate=3600`，数据更新最长延迟 1 小时（模型价格/评分天级更新，可接受）。

### 5.2 架构约束（回归红线）

1. **渲染树禁携动态 API**：`cookies()/headers()` 不得出现在 ISR/静态路由的 RSC 渲染树中（Next 14 非 PPR 无动态洞机制，运行时触发 static→dynamic 硬错误 500）。头部登录态由客户端槽位 `HeaderSession`（探测 `/api/v1/auth/me`）承担。
2. **loading.tsx 边界**：`(web)` 路由组与 `/models/[slug]` 必须保留 loading 边界——既是导航反馈，也是 Link 预取生效的前提（动态路由预取只到最近 loading 边界）。
3. **首屏禁 `opacity-0` 初始态**：进场动画一律纯 CSS（`.reveal-in`，200ms），SSR HTML 即可见态，禁止 JS 状态驱动点亮。
4. **语义化链接**：可跳转的列表单元格必须 `<Link>`（爬虫可发现 + 预取）；canvas 图表点击可保留 `router.push`（妥协项）。

### 5.3 M-PERF 实测基线（prod，本机）

|---|---|---|

| `/models` 重定向环 | 308 环 + `/aidean` 404 | 已拆除，直连 200 |

### 5.4 环境教训（Windows）

- `.pnpm` 存储中 `next/dist` 曾两次在 prod server 进程被强制终止后消失（依赖链接损坏 → `Command "next" not found`）；恢复手段 `pnpm install --force`。预防：终止服务优先温和方式；遭遇 `next not found`/jest-worker processChild 缺失时先 `pnpm install --force` 再排查。

### 11.2 四个判据边界（写入测试验收，防误判）

#### 11.2.1 strict-mode 根因（`getByText` 松散匹配命中 2 节点）

- **现象**：e2e `console-flow-gradient.spec.ts` 偶发 `strict mode violation: getByText('当前等级') resolved to 2 elements`。
- **根因**：宽松文本匹配命中 **2 个节点**（一个可见、一个隐藏），Playwright strict mode 要求唯一 → 报错；两次 run 的 DOM 就绪时序不同 → 时红时绿（**flaky**，非缺陷）。
- **修复**：定位串加 `{ exact: true }` → 收敛为 1 个节点。
- **实证**：`scratch/_qa01/exact-probe.mjs` 实测「松散=2 / exact=1」；门禁 G3.3 连续 3 轮复跑全绿（`2✓ 2✓ 2✓`）证其**真实止 flake**，非单轮侥幸。
- **纪律**：凡断言文案类文本，一律 `exact:true`；出现 `strict mode violation` 先判「匹配多重」再判「元素缺失」。

#### 11.2.2 主题默认态边界（判据用 computed `--primary`，非 `data-theme` 属性）

- **实现**：`uiStore` 初值 `indigo`；`hydrateUiFromStorage()` **仅当** localStorage 存在**有效**值时才写 `documentElement.dataset.theme`。
- **边界**：因此「无存储」与「存储非法值」两种状态下 `data-theme` 属性为 **null（缺省）**，而**视觉仍是 indigo**——由 `:root{--primary:#4f46e5}` 兜底。
- **判据**：默认态判定**必须**用 `getComputedStyle(documentElement).getPropertyValue('--primary')`（+ `aria-pressed`）为真值；**不可**以「`data-theme==='indigo'`」作判据（会误判为 FAIL）。门禁 T1/T6 即按此口径。

#### 11.2.3 豁免「双 404」（Pages Router 遗留路径）

- `/_next/static/chunks/webpack.js`、`/_next/static/runtime/main.js` 为 **Pages Router** 才产出的路径；本项目为 App Router，**本就不产出 → 恒 404 属正常**，不计资源缺失。
- 门禁 H5 把这 2 条作为**显式豁免 404 断言**（期望 404），与 H4「其余 `/_next/static/**` 全部 200」分离，避免误报。

#### 11.2.4 视口前置（ThemeSwitcher ≥640px）

- `ThemeSwitcher` 位于 `hidden … sm:flex` 容器，**仅 ≥640px 可见**。
- 门禁 T 段固定 `viewport {1280×800}`；若在窄视口跑主题断言会出现「按钮不可见→点击超时」的**假红**。**纪律**：主题相关 e2e/探针一律 ≥640px。

#### 11.2.5 抖动重试纪律（区分终态与瞬时抖动）

- 门禁在 HTTP 层统一走 `getWithRetry(url, expect, tries=3)`：首次非期望码时**间隔 1.5s 重测至多 2 次**，两次仍不符才记 FAIL。

### 11.4 生产换基址（`NEXT_PUBLIC_SITE_URL`）复验步骤

> 背景：`AUTH_ISSUER = NEXT_PUBLIC_SITE_URL ?? "http://localhost:3000"`，该值**构建期内联**；authorize/consent/middleware 的绝对重定向 origin 源自它（**不再**回显 Host 头，杜绝 `0.0.0.0` 与 Host 伪造）。故**换基址必须重建**，运行期改环境变量无效。

### 13.1 NODE_ENV 显式纪律（本轮新增，防「假失败」）

- **纪律**：**凡在宿主运行 vitest / playwright / 任何调用自身逻辑的脚本，必须显式前缀 `NODE_ENV=test`**。
- **机理**：宿主 `NODE_ENV` 实测为**空串**（非 `development`、非 `production`）。应用内计费/渠道判定函数 `channelOf()` 在宿主「生产口径」下会抛 `40000`，使**充值/支付链路的 5 用例集体假失败**——与产品回归无关，纯属运行环境口径缺失。
- **反例（务必避免）**：`npx vitest run`、`npx playwright test`（不带前缀）在宿主直接跑 → 计费相关用例整片红。
- **正例**：`NODE_ENV=test npx playwright test --config playwright.config.ts --project=web`。
- **与 standalone 口径的区别**：standalone `server.js` 固化 `NODE_ENV=production` 语义，**不能**用 `NODE_ENV=test` 起服（会破坏生产/非生产分支判定）；dev mock 支付渠道仅非生产可用。二者口径**不可混用**。

### 13.2 限流污染分诊流程（每次跑 e2e 前的固定前置）

`LOGIN_IP_RATE_LIMIT = 20 / 600s`（Redis 键 `rl:login:{ip}`）。同进程内连续登录会**累积**该窗口 → 触发 429 级联。

**标准分诊三步（串行）**：

1. **清键**：`node apps/web/scripts/clear-rl.mjs`（输出 `cleared=N`；N>0 说明确有残留窗口）。
2. **单跑**：`NODE_ENV=test npx playwright test --config playwright.config.ts --project=web --workers=1 --reporter=list`。
3. **对表**：结果应回归 **40 passed / 0 failed / 71 skipped**（QA-GATE-02/QA-COV-01 冻结口径）。若 failed > 0，**先怀疑限流未清**而非产品回归。

**判据边界**：限流污染的特征是**同一文件内多个登录用例连片 429**；产品回归的特征是**断言值不符**（非 429/非 40000）。两者混淆是本项目历史最主要的「假红」来源。
