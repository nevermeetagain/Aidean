## 排序理由（先解锁依赖多的、先做不确定性高的）

1. **S0 第一（步行骨架）**：TASK-001 是 51 张卡的功能依赖祖先，TASK-006 是 24 张卡的祖先（脚本计算）；无真库 e2e，任何切片的 Done 都无法被独立验证者复现。六要素：就绪探针（003）+ 鉴权写（既有 POST /user/api-keys，005 端到端复验）+ 一张表（api_keys）+ 一次迁移（空库重放，006）+ 前端打真实 API 的页面（/user/console）+ 统一错误响应（001/002/005）。项目已有骨架，S0 是「复验 + 加固」，不新建业务表（§13.13）。
2. **S1 第二**：已确认缺陷，且是 S4 的硬前置；不确定性已由 PGlite 降低，但真 PG16 结论仍需 010 固化。
3. **S2 第三**：MUST、风险高（改网关/测评入口），其 requireFeature 被 S3 复用。
4. **S3、S4a**：S3 依赖 S2；S4a 依赖 S1；S3 与 S4 同改模型详情页 → S3 UI 先。
5. **S4b 在 U-15 后**：资金路径变更 + 反证未排除（ADR-P005），必须等裁决与盘点；但其盘点卡 049 不等裁决，尽早给用户数据。
6. **S5/S8/S9 条件刀**：外部输入到位前不下发。
7. **S6 穿插**：只测量不优化（§9.1）。
8. **S7 收尾**：依赖裁决且文档资源锁天然在末段；RTM 入库（051）是本轮「统一规划体系」的落地点。
