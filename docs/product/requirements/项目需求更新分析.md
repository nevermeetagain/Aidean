## 二、苏格拉底追问 + 双向钢人论证

### 2.1 苏格拉底追问（4 轮）

**第 1 轮：追现象**

> 问：6 个 adapter 文件存在但未注册，意味着什么？
> → 答：代码资产已先行开发但未被消费——注册表与代码脱节。
> → 问：为什么文件存在却没有注册？是 API 不可用还是忘了？
> → 答：需要检查每个 adapter 的 fetchUrl 是否可用——如果可用则纯遗漏，如果不可用则凭据/API限制。

**第 2 轮：追影响**

> 问：如果 6 个 adapter 永远不注册，会怎样？
> → 答：6 个文件成为 dead code，维护负担但无运行时影响；采集覆盖面只有 3 源。
> → 问：3 源够用吗？
> → 答：openrouter（价格+能力）/huggingface（开源生态）/lmsys（竞技场）确实覆盖了核心维度，但 epochai/llmstats/artificial-analysis 是评测榜单数据，agentindex/skillsmp/smithery 是 agent/工具市场数据——这些是扩展维度，缺了影响数据丰富度但不影响基本功能。
> → 问：那注册它们的优先级是什么？
> → 答：epochai/llmstats/artificial-analysis 与现有 benchmarks 域关联（评测数据），优先级高；agentindex/skillsmp/smithery 与 tools 3 页面关联（需先有页面），优先级中。

**第 3 轮：追根因**

> 问：check-docs-facts.mjs 期望值漂移为什么没被发现？
> → 答：因为 CI 可能用的是 check-docs-rule.mjs（含自己的数字断言）而不是 check-docs-facts.mjs；或者 CI 中 facts 失败但被忽略。
> → 问：两个 checker 有什么区别？
> → 答：check-docs-facts.mjs 是独立的数字真源断言脚本（10 项）；check-docs-rule.mjs 是铁律检查 + L4 扩展数字断言（涵盖 .md 文件治理 + 部分数字校验）。两者部分重叠。
> → 问：那应该统一还是保留两个？
> → 答：保留两个但职责分工——facts 专注数字真源（route/page/spec/model/ui-refs count），rule 专注文档治理铁律（.md 文件位置 + 实体文档唯一来源）。两者重叠部分以 facts 为准。

**第 4 轮：追边界**

> 问：非 admin 组件 @aidean/ui 迁移的工作量到底多大？
> → 答：36 个组件中，home(9)/site(8)/ladder(6) 是高可见度，console(8) 是用户中心，models(1)/evaluations(1)/common(3) 是单点。高可见度的 23 个组件迁移工作量适中。
> → 问：迁移的风险是什么？
> → 答：@aidean/ui 的 Button 可能带样式注入（variant/size props），直接替换原生 `<button>` 可能影响样式。需要逐个检查 className 是否冲突。
> → 问：那是否应该全部迁移？
> → 答：不——`<div>` 和 `<span>` 不需要迁移（它们不是 @aidean/ui 的组件范围）；只有 `<button>`/`<input>`/`<table>`/`<dialog>` 等可迁移。优先迁移 Button 和 Table 类组件。

### 2.2 双向钢人论证

**正方论点：应该注册全部 6 个 adapter**
- 理由：文件已存在 = 代码资产已投入，不注册就是浪费；扩展采集覆盖面到 9 源
- 拆解：多源数据是交叉验证的前提，3 源太少不足以做加权融合

**反方钢人：不应该注册全部 6 个 adapter**
- 理由：某些 adapter 可能 API 不可用或需要付费凭据，盲目注册会导致 sync 报错；6 个 adapter 对应的数据源可能重复（epochai/artificial-analysis/llmstats 都是评测榜单）
- 拆解：应该先验证每个 adapter 的 API 可用性，只注册可用的

**综合判决**：
- 先验证 6 个 adapter 的 API 可用性（fetchUrl 是否返回数据）
- 可用的立即注册，不可用的标注「需凭据/需 API key」并登记
- 去重考虑：epochai/artificial-analysis/llmstats 评测数据源虽有重叠但各有特色（epochai 专注公开评测，artificial-analysis 有推理速度，llmstats 有统计聚合），保留全部
- **最终结论**：注册全部 6 个，但每轮 sync 失败的 adapter 自动跳过并在 SyncManager 标注错误状态

**正方论点：应该修复 check-docs-facts.mjs 的 Windows 兼容性**
- 理由：跨平台兼容是基本要求；开发者可能用 Windows

**反方钢人：不应该修复，因为 CI 是 ubuntu-latest**
- 理由：CI 门禁在 Linux 运行，Windows 本地开发者可以不跑 facts-checker
- 拆解：但如果 facts-checker 在 Windows 报错，开发者会误以为是代码问题而非工具链问题

**综合判决**：
- 修复 Windows 兼容性——因为 facts-checker 的价值在于开发者本地也能跑
- 但优先级降为 P2——因为 CI 在 Linux 上运行，Windows 兼容性不影响 CI 绿灯
- **最终结论**：修复期望值漂移（P0）+ desc 一致性（P0），Windows 兼容性（P2）
