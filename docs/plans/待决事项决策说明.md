## 〇、总原则：什么叫「现在不修」

对全目录非 ✅ 项逐一检视时，用同一条标准判断：**「我现在动手，是修好它还是搞坏它？」** 落入以下三类之一的，登记原因与重启条件后挂起，而不是硬修：

| 类别 | 含义 | 通俗说法 | 涉及项 |
|---|---|---|---|
| 一、缺材料 | 修复所需的外部输入尚不存在，硬写就是空壳或无法验证 | 等家长送钙片 | #13、#34、#65 |
| 二、要审批 | 修复动作触发项目规矩（ADR 评审 / 管理者决策权），先斩后奏即违规 | 动手前要家长签字 | #23、#17（v1.2：#30 已移出） |
| 三、工程大 | 属于需独立立项排期的重构/新功能，塞进修复轮会改崩 | 不是换灯泡，是重新布线 | #35、#43、#36 |

### #13 back-channel 单点登出（全量一致性验收）

- **问题**：主平台作为登录中心（IdP），用户在主平台退出时，需要把「已退出」通知到所有子平台（OIDC back-channel logout），否则子平台侧会话残留。
- **已完成**：`sendBackChannelLogout` 已加 2 次重试（间隔 500ms，单次 5s 超时），best-effort 语义已文档化（目录原文，L2-3 轮）；v2.4 轮 D2 同轮收口了 run-due 鉴权双通道。
- **缺口**：「全量 OIDC back-channel 一致性验收」需要**产品侧提供 logout 端点并配合验收**——代码侧无缺陷可修，缺的是验收对象。
- **不修理由**：第一类（缺材料）。验收依赖外部系统就绪。
- **建议**：无需动代码；把「子平台 logout 端点清单」列入子平台接入验收模板（`docs/product/modules/子平台SSO接入指南.md` 可加一节）。
- **重启条件**：产品侧 logout 端点就绪。

### #34 多源交叉验证加权融合（D5）

- **问题**：采集管线设计里有「多个数据源对同一模型字段做加权融合」的能力（schema 已有 `weight` / `isWeighted` / `scorePercentile` 字段），用于提升数据置信度。
- **已完成**：CrossValidator（`apps/web/lib/sync/` 下 cross-validator.ts，目录原文 2026-09-23 L3：5104B）已实现多源字段级比对 + 容差配置（价格 ±5%）+ 冲突报告。
- **缺口（v1.2 改写）**：数据源并不单一——9 个 adapter 已注册且 v9.0 轮实抓 458 条成功落库；真阻塞是**跨源模型身份不统一**：各 adapter 的 modelCode 推导各异（`adapters/openrouter.ts:30` 用 `m.id`、`huggingface.ts:66` 用 `m.id`、`artificial-analysis.ts:58` 用 `m.model ?? m.name`、`agentindex.ts:62` 用 `a.id ?? a.slug ?? a.name`），同一模型跨源 key 必不同 → `cross-validator.ts:96` 的 `sources.length < 2 continue` 恒触发 → 冲突报告恒为空。另：加权融合本体未实现（schema `weight/isWeighted/scorePercentile` 零消费，实测确认）。
- **不修理由（拆两半）**：**#34a 身份归一**不受外部材料阻塞（纯函数 + mappers 层双字段，回归面最小），列入实施排期；**#34b 加权融合**维持第一类挂起——归一覆盖率未知前实现了也无法验证。
- **建议**：先做 #34a（`canonicalModelKey` 归一 + mappers 层产出 `rawCode/canonicalKey` 双字段 + 9 源实抓覆盖率报告）；#34b 重启条件改为「归一后同 key 多源覆盖率 > 0 且冲突样本足够」。
- **重启条件**：#34a 完成且覆盖率报告 > 0。

### #30 自动调度（scheduled_scripts 驱动的 cron）——**v1.1 判定修正：代码侧已完成，移出挂起清单**

- **v1.1 实测刷新**：原判定「没有任何进程在消费 nextRunAt/cronExpression」**过时**。当前代码侧已全链路闭环：
  - 消费者：`docker/scheduler/entrypoint.sh`（R-70）——alpine crontab 每分钟 `curl -X POST -H "Authorization: Bearer ${ADMIN_API_TOKEN}" .../api/v1/admin/scripts/run-due`；
  - API：`app/api/v1/admin/scripts/run-due/route.ts:18-33`——D2 双通道鉴权（Bearer 内部令牌 ∥ 管理员 Cookie）；
  - 执行器：`lib/features/admin/script-executor.ts:123-138`——`runDueScripts()` 按 `isActive + nextRunAt <= now` 取到期脚本逐个执行，执行后重算 nextRunAt（v9.0 轮手动触发「排名更新」实测下次执行已重算）。
- **结论**：#30 由「🟡 待 ADR」改为 **✅ 代码侧闭环**；零新依赖（未引 node-cron，铁律 5 无涉），不属「要审批」类。
- **余项**：仅生产 compose 实弹验证（sidecar 容器真正跑起来），归 **#2 部署实弹**；dev 非 compose 环境无 sidecar 属预期（本地手动触发已够用）。
- **v1.2 补记（收口轮实测）**：设计真源《功能设计文档》§3.4.1(F):178 要求的「单实例互斥锁（Redis SETNX，TTL=脚本最大时长）」当时未实施——`script-executor.ts` 全链路无锁，执行中脚本（>1 分钟）会被 sidecar 每分钟重复拉起（5 分钟窗口最多 5 并发）；已登记 **#69** 并获管理者批准修复（run-due 入口 `lock:scheduler:run-due` TTL=300s + 值比对原子释放 + Bearer 改 `timingSafeEqual`），修复回执见台账 §7.11。另 sidecar `entrypoint.sh` 非 200 仅打日志、无重试/告警，归 #2 实弹一并验收。
