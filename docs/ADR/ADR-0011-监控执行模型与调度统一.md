# ADR-0011：监控执行模型与调度统一——运行请求意图表 + run-due 单一判定

> 状态：已接受 | 日期：2026-10-23 | 关联：V0.12.0 T120-10/11/12/13/14、B11-08（ScheduledScript 执行链）、REQ-M-002 / REQ-M-009 / REQ-M-011

## 一、背景

1. V0.11 的「立即运行」（`POST /api/v1/admin/monitoring/sources/{key}/run`）只占 Redis 锁 `lock:monitor:run:{key}`（TTL 300s）后返回 202，没有任何进程消费这个意图：按钮按下后不会真的跑，锁过期即丢失。
2. 监控源的 `cadenceCron` 已存于注册表，但没有调度器读取；B11-08 已建好 `ScheduledScript` 表、`executeScript` 与 sidecar `run-due`（仅 fx 脚本在用）。
3. web 进程与 sidecar 是两个进程，web 里不能长跑采集（请求超时、部署重启即中断）。

## 二、决策

**「立即运行」改为写一行意图，由 sidecar 消费；周期运行统一走 B11-08 的 run-due。不引入消息总线，DB 行即事件。**

### 2.1 运行请求表 `monitor_run_requests`

- 字段：`id, source_key, status(pending|running|done|failed), requested_by, created_at, started_at, finished_at, result_count, error`（契约 `MonitorRunRequest`）。
- 幂等键：部分唯一索引 `(source_key) WHERE status IN ('pending','running')`，同源同时至多 1 个未完成请求；重复 POST 捕获唯一冲突 → `10006`（429），沿用 V0.11 锁语义对外不变。
- 状态机：`pending → running`（领取）、`running → done | failed`；其余迁移非法（契约 `MonitorRunTransition`）。

### 2.2 消费

- 领取：`UPDATE monitor_run_requests SET status='running', started_at=now() WHERE id = (SELECT id … WHERE status='pending' ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED) RETURNING *`，原子、多实例安全。
- 时机：run-due 节拍（每 15 分钟）与每次 `monitor_catalogs` 脚本执行开头各领取一次。
- 僵死回收：领取前把 `running` 且 `started_at < now() - 30min` 的行置为 `failed(error='stale')`。

### 2.3 周期运行

- `monitor_catalogs` 作为一条 `ScheduledScript` 注册（T120-11 迁移，幂等插入），由 run-due 到点执行；各源 `cadenceCron` 在脚本内按 Asia/Shanghai 判定是否到期。
- 源列表的 `nextRunAt` 为只读派生值（`cadenceCron + lastRunAt`），非法 cron → `null`，不入库。

## 三、备选与否决

| 备选 | 否决理由 |
|---|---|
| web 进程内直接执行采集 | 请求超时与部署重启会中断；与 V0.11「web 不长跑」原则冲突 |
| Redis 队列 / BullMQ | 新增依赖与运维面；单源低频场景用 DB 行即可满足，且可审计、可分页查询历史 |
| 保留 Redis 锁 + 发布订阅 | 订阅者离线即丢消息，无历史 |

## 四、后果

- 正面：「立即运行」真正可用且有历史（`GET …/runs`）；周期与手动共用一条执行链；无新依赖。
- 代价：手动运行最长延迟一个节拍（≤15 分钟）；在 UI 上以「已排队」状态表达（T120-15）。
- 迁移顺序：`20261024000000_monitor_run_requests`（T120-12）先于 `20261024010000_monitor_catalogs_script`（T120-11）。
