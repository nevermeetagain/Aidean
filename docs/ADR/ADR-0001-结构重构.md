# ADR-0001 · 主平台项目结构与文档体系重构

- **状态**：已采纳（Accepted）
- **日期**：2026-08-18
- **决策人**：EDY（产品/架构）、WorkBuddy（执行）

## 一、背景（Context）

`.example/history/` 下积累了大量半成品，呈现"多版本 + 多 IDE 副本"的散落状态：

- `AigcLadderDiagram/`：主平台（Next.js 全栈），含 `Aidean_0506`、`AigcLadderDiagram`、`AigcLadderDiagram - history` 三个版本。
- `AideanSynapse/`：子平台（API 中转站，Go + 前端），含 `hermes/omp/opencode/trae` 五个 IDE 副本。

问题：无法维护、文档与代码漂移、不利于统一治理与后续迁移。

## 二、决策（Decision）

1. **范围收敛到主平台**：本轮只重构 **Aidean 主平台（AigcLadderDiagram）** 的结构与文档；子平台（synapse/ragwiki/twin）暂不纳入。
2. **本轮只建结构与文档，不搬动代码**：在根 `docs/` 落地一套完整、可直接用的开发文档；历史代码继续保留在 `.example/history/`，作为后续迁移的详实底稿。
3. **`.example/history/` 保持不动**：明确其为"历史参考"，不删除、不重命名，降低风险、保留回溯能力。
4. **主平台采用"单一应用仓库"形态**：因当前仅主平台一个代码平台，不强行上 monorepo；《目录结构文档》给出主平台的标准 Next.js 应用布局，并预留向 `apps/web` monorepo 升级的路径（见"升级路径"）。

## 三、理由（Rationale）

- 历史文档已非常完整（需求/功能/目录结构到 v6.5），重做成本高于"精修 + 收敛"，故以整合为主、重写为辅。
- 子平台尚无稳定代码（synapse 仅多 IDE 副本、ragwiki 为外部 RagFlow、twin 未启动），纳入 monorepo 反而增加当前复杂度。
- 不动历史代码：避免在"规划阶段"引入不可逆的文件搬迁风险；先固化结构蓝图，再按蓝图迁移。

## 四、后果（Consequences）

- **正向**：文档有了唯一真源与清晰导航；结构蓝图可指导后续代码迁移；历史代码零风险保留。
- **待办**：后续需按《目录结构文档》将 `.example/history/.../AigcLadderDiagram` 的最成熟变体迁入新结构，并删除冗余副本。
- **约束**：若未来纳入子平台，应升级为 pnpm + Turborepo monorepo（`apps/web`、`apps/synapse` 等），届时本文档中心相应扩展为"总—分"两层。

## 五、升级路径（未来可选）

```
当前：单一应用仓库（主平台代码在仓库根或 apps/web）
  ↓ 当 synapse / ragwiki / twin 进入开发
未来：pnpm + Turborepo monorepo
  apps/web        ← 主平台（本仓库当前内容）
  apps/synapse    ← API 中转站（合并 5 个 IDE 副本为 1 个规范版）
  apps/ragwiki    ← 知识库（基于 RagFlow，仅集成与配置）
  apps/twin       ← 数据分身（规划中）
  packages/       ← 跨平台共享类型 / UI
  deploy/         ← 全局编排（base + 各平台 compose）
```
