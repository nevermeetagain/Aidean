## 1. 工作包与角色

## 3. 调查结果

### 3.1 审计根因被证伪（关键）

任务输入中的审计结论为「**discovery 宣告 `localhost:3000` 导致 3333 容器侧 token 目标不可达，进而 callback 后会话无法建立**」。实地调查**不支持**该结论：

- `AideanBot/backend/app/providers/aidean/client.py` **不消费 discovery**（全文无 `/.well-known/openid-configuration` 调用）。其构造采用**双基址**：
  - `_base_url` ← `AIDEAN_ISSUER`：服务端对服务端端点（`/oauth/token`、`/oauth/userinfo`、`/api/v1/internal/billing/wallet`、`/oauth/revoke`）**直连**，容器侧可达；
  - `_public_base_url` ← `AIDEAN_PUBLIC_URL`（空串回落 `_base_url`）：仅用于 `authorize_url()` 签给宿主浏览器的 302 Location。
- 源码注释（`client.py:85-86`）已明确此分离语义：「基址用 `_public_base_url`（浏览器侧）：签给宿主浏览器的 Location 必须浏览器可达（如 localhost），不能用容器侧 `host.docker.internal`」。
- 运行时实测（§9 E4）：`AIDEAN_ISSUER=http://host.docker.internal:3000`、`AIDEAN_PUBLIC_URL=http://localhost:3000` → **双变量契约（A-T21/A-T22 裁决 B）已正确落地**。

因此 `discovery.issuer=localhost:3000` **不会**污染 3333 的 token 目标；token 目标恒为容器可达的 `host.docker.internal:3000`。

### 3.2 `/auth/me 401` 的真实诱因

复现并定位到两类**环境/操作级**诱因，而非代码回退：

1. **测试用自造 `state`**：首轮手工 callback 返回 `400 {code:10002,"state 缺失、已过期或不匹配"}`——因未经 3333 后端签发流程。修复：先 `GET 3333 /api/v1/auth/login` 取后端签发 `state` 并复用。
2. **系统代理拦截 `host.docker.internal`**：`curl` 经系统代理导致 `host.docker.internal:3000` 502。修复：`--noproxy '*'`。

修正上述两点后，全链路一次打通（§9 E13）。

### 3.3 真实链路（已验证，脱敏）

```
① 3333 GET /api/v1/auth/login                         → 302 <AIDEAN_PUBLIC_URL>/oauth/authorize?...&state=<signed>&redirect_uri=localhost:3333/.../callback
② 主平台 GET /oauth/authorize（未登录）                → 307 /login?redirect=...
③ 主平台 POST /api/v1/auth/login（邮箱+密码）          → 200 {code:0}，种 aidean_token / aidean_refresh
④ 主平台 GET /oauth/authorize（带会话 + 同 state）      → 307 http://localhost:3333/auth/aidean/callback?code=<masked>&state=<masked>
⑤ 3333 GET /api/v1/auth/callback?code&state           → 200 {code:0}，种 aideanbot_session
⑥ 3333 GET /api/v1/auth/me                            → 200 {user:{email:admin@…,tier:NORMAL,role:SUPER_ADMIN}, wallet:{balanceYuan:"1000.00"}}
```

`token` / `userinfo` / `wallet` 三跳由 3333 后端经 `AIDEAN_ISSUER=host.docker.internal:3000` 完成（容器→宿主可达）。

## 5. 设计决策

### 5.1 地址语义模型（§9.1 交付物）

| 场景 | 发起方 | 目标 | 正确基址 | 依据变量 |
|---|---|---|---|---|
| 用户点击子平台登录 | 宿主浏览器 | 主平台 authorize | `http://localhost:3000` | `AIDEAN_PUBLIC_URL` |
| 主平台登录页 / 302 回跳 | 宿主浏览器 | 3333 callback | `http://localhost:3333` | `OIDC_REDIRECT_URI` + 白名单 |
| 子平台后端兑换 token | 3333 容器 | 主平台 token | `http://host.docker.internal:3000` | `AIDEAN_ISSUER` |
| 子平台后端查 userinfo/wallet | 3333 容器 | 主平台 userinfo/wallet | `http://host.docker.internal:3000` | `AIDEAN_ISSUER` |
| 主平台自述端点 | 任意 RP 后端 | discovery/JWKS | issuer 同源 | `NEXT_PUBLIC_SITE_URL` |
| 容器内自指 | 3333 容器 | 自身 3000 | `http://localhost:3000`（容器内） | — |

**核心不变量**：

1. **浏览器侧基址与容器侧基址必须分离**：`localhost` 对宿主浏览器可达、对 3333 容器不可达（容器内 `localhost:3000` 命中自身）；`host.docker.internal` 反之。任何「统一为单一变量」的方案都会在某一侧失效——这正是禁止全局 `localhost → host.docker.internal` 替换的原因。
2. **issuer 声明与实际直连解耦**：RP 不依赖 discovery 决定 token 目标，故 issuer 文案不构成契约阻断。
3. **端口语义**：3333 容器映射 `0.0.0.0:3333 -> 3000`，容器内部监听 `3000`；宿主访问子平台须用 `:3333`。

### 5.2 最小契约调整（§9.2）——**结论：无需调整**

| 候选调整 | 判定 | 理由 |
|---|---|---|
| 把 `AIDEAN_ISSUER` 统一改为 `localhost:3000` | **否决** | 容器侧不可达，将使 token 兑换失败——即审计建议的误方向 |
| 把 `AIDEAN_PUBLIC_URL` 统一改为 `host.docker.internal:3000` | **否决** | 宿主浏览器不可达（502） |
| 让 RP 消费 discovery 决定 token 目标 | **否决** | 引入单点依赖且当前实现更稳（双基址显式）。如未来需要，应作为**可选**能力，不得替换直连 |
| 现状（双变量分离） | **保留** | 已实测双环境全绿，改动无收益、有回归风险 |

### 5.3 跨环境验证口径（§9.3）

| 环境 | 形态 | 浏览器侧基址 | 容器侧基址 | 状态 |
|---|---|---|---|---|
| 宿主本地 dev | `next dev` @3000 + 3333 容器 | `localhost:3000` | `host.docker.internal:3000` | **已实测 3/3 PASS** |
| 容器/本地混合 | standalone @3000 + 3333 容器 | `localhost:3000` | `host.docker.internal:3000` | 协议链路已实证；见 §10 遗留 L1 |
| 生产 | 公开域名 + 容器 | `https://<公开域名>` | 同域名或内网反代 | 待 REL-01 落地（口径见下） |

**生产落地口径**：`NEXT_PUBLIC_SITE_URL`（→ `AUTH_ISSUER` / discovery issuer）与 `AIDEAN_PUBLIC_URL` 指向**公开域名**；`AIDEAN_ISSUER` 指向**容器可达入口**（内网名或公开域名，视部署拓扑）；`OIDC_REDIRECT_URI` 必须落在 `oidc_clients.wechat-rag.redirect_uris` 白名单内（精确匹配）。

### 5.4 Cookie 安全语义（未放宽）

- 主平台：`baseCookieOptions()` = `{ httpOnly: true, sameSite: "lax", secure: isProduction(), path: "/" }`；
- 实测属性（dev）：`aidean_token` / `aidean_refresh` 均 `HttpOnly; SameSite=lax; Path=/`；dev 无 `Secure`（`isProduction()` 为假），生产自动 `Secure`；
- 3333：`aideanbot_session` 为 HttpOnly 会话 Cookie；
- **未做任何放宽**。注：`http://localhost` 在 Chrome 中属 trustworthy origin，故生产 `secure=true` 下 e2e 于 localhost 仍可种 Cookie。

## 10. 遗留问题与风险

### 遗留问题

- **L1（配置级，非本包阻断）standalone 形态下 authorize 未登录 307 的 Location 主机名**：
  standalone `server.js` 硬编码 `const hostname = process.env.HOSTNAME || '0.0.0.0'`，且 `nextConfig.experimental.trustHostHeader` 未开启 → 重定向 Location 取**配置 hostname 而非请求 Host 头**，实测为 `http://0.0.0.0:3000/login?...`（宿主浏览器不可达）。dev 形态无此问题（E7 为 `localhost:3000`）。
  - 本包影响：被 `sso-3333.spec.ts` 的响应拦截器兜底（`0.0.0.0 → localhost`），故不阻断三条用例；
  - 生产建议：由 **REL-01** 以「显式固定 hostname（如 `HOSTNAME=0.0.0.0` + 开启 `trustHostHeader`）或反向代理改写 Location」落地，属**主平台运行契约**，不在本包越界修改。
- **L2（部署口径）discovery issuer 的生产覆盖**：本地 `localhost:3000` 正确；生产须由 `NEXT_PUBLIC_SITE_URL` 覆盖为公开域名（已设计，未改）。

### 风险

- **R-a 并发 agent 干扰（环境级）**：执行期观测到 `.next` 被并发进程改写（`trace` 1 分钟内 17KB→593KB）、`test-results/` 被同期占用、3000 端口由外部 dev 进程提供。本包结论建立在「双服务可用的时间窗口」内，重跑需确认 3000/3333 在线且为同一契约。
- **R-b `test-results` 守卫**：Playwright 启动即清理 `test-results/`，触发 safe-delete 失败（`trash` aborted）。规避：预改名隔离（§6）。**建议 REL-01 在 CI 中改 `outputDir` 或预清理**。
- **R-c dev 与 production 形态差异**：本包主链路在 dev 形态实测全绿；生产 standalone 形态须复核 L1。
