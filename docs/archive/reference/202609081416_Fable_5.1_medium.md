# 第二轮（收敛与拷问）：苏格拉底式致命追问 + 双向钢人论证

## N1 · 「先收口在途 spec」是否是伪前提？（拷问 Part 0）

**致命追问**：Phase 2–4 代码已写完，直接勾选不就行了？为什么 VERIFY 要单独立阶段？
**反方钢人（合并派）**：代码都在，收口只是形式主义；直接在 Part 1/2 的 change-id 里顺带验证更省一轮流程。
**正方钢人（先行派）**：① 六步循环明文规定 IMPLEMENT 未过 VERIFY 不得 CLOSE，且「L2 勾选 = 全部 L3 完成并经 checklist 通过」——不验证就勾选=伪造证据；② 这 17 个 admin route **零专属单测**（现有 spec 仅 middleware/admin-guard/admin-routes），验收标准（并发双花、幂等、封禁 ver++、CSV 导出）全部依赖尚未写的测试；③ 工作区未提交状态下叠加新改动，一旦出现经验教训.md §一 的 .pnpm 损坏类事故，回滚点不存在。
**裁决**：先行派胜。Part 0 = 收口在途 spec（补测→取证→勾选→提交），这是后面一切的回归基线。

## N2 · 前端重设计的半径多大？（拷问 Part 1）

**致命追问**：「界面 Low 要重设计」——是推倒重做还是改皮？天梯图刚经历 v1.7→v2.1 七轮用户验收迭代，重做是否等于销毁已验收资产？
**反方钢人（重做派）**：用户明说「使用 Skills 重新设计和实施」，且 1.2 要求参考站重构功能；保守改皮无法满足「Low」的判词。
**正方钢人（分层派）**：① 用户历史需求 num:0–6 显示天梯图交互细节被逐像素验收过（工具栏三行制、轴位三态、分度值、无限滚动）——交互层是资产；② 经验教训 §一.4 明文规定工具栏改动必须对照基线、以界面交互文档为唯一口径；③ 「Low」的痛感来自视觉层（令牌/排版/留白/层次）而非交互层。
**裁决**：分层派胜。**交互逻辑冻结、视觉皮肤重做**——天梯页只动 CSS/令牌/组件观感，不动数据流与工具栏结构；营销页（首页/banner/关于等）可更大胆重排。此裁决写入 spec 的「不变式」节，防止实施时越界。

## N3 · 管理端深色 → 浅色是否要回退刚建好的东西？（拷问决策点 D1）

**致命追问**：在途 spec 刚把管理端建成深色外壳（`(admin)/layout.tsx` 用 `bg-slate-950`），现在按 3.2 改浅色是不是自相矛盾？
**反方钢人（保留深色派）**：管理端深色是与前台差异化的既成决策，且管理员长时间盯表格深色护眼；3.2 说的是「默认」——管理端可以例外。
**正方钢人（改浅色派）**：① 用户原话「前后端UI设计，默认以浅色/冷色等为主，不要使用深色为默认风格」没有给管理端开例外，且这句话在本任务里**晚于**深色决策出现，按「序号最大为准」（UpdatedHistory.md 文首规则）应理解为推翻深色；② 深色只是 Tailwind 类名换层皮，改造成本低（侧边栏布局、信息架构这些真正值钱的东西不变）；③ 前后台差异化的本质是**布局与信息架构**（侧栏/顶栏/数据表），不是配色。
**裁决**：改浅色冷色（slate/indigo 冷色系），保留管理外壳布局。列入决策点 D1 请用户确认，若用户坚持深色则仅改前台。

## N4 · 「以数据库-表为基础」到底覆盖到哪？（拷问 Part 2 范围）

**致命追问**：35 个 model 全部建管理面是 6+ 个 change-id 的量，用户要的是「完善」还是「全覆盖」？
**反方钢人（全覆盖派）**：2.1 说「不能对本项目核心功能进行管理」——凡库表皆可管理才算闭环；审计 §8.5 的缺失矩阵就是全域清单。
**正方钢人（分层派）**：① 开发流程的增量展开规则明文允许中期只到 L2+关键 L3；② 审计 §8.5 已给出 P0/P1/P2 分级（发布前必需/运营必需/二期），这是经过裁决的优先序；③ 部分 model（如 `usage_logs` 大表、`sync_batches`）的合理管理形态是只读查询而非 CRUD。
**裁决**：分层派胜，但清单必须**穷举**（用户要看到全部表的去向）：每个 model 归入某个 Phase 的某个管理域，标注 CRUD/只读/挂账三态。P0 = 发布前必需（用户/订单/模型/财务只读），P1 = 运营必需（Key 池/计费规则/免费额度/权重/公告/配置），P2 = 二期（同步任务细节/工单回复/审计深查）。

## N5 · 「使用 Skills」是口号还是硬约束？（拷问 Part 1/2 实施方式）

**致命追问**：Skill 只是提示词模板，写进方案是否制造流程负担？
**反方钢人（弱约束派）**：Skill 内容与项目文档可能冲突（如 frontend-design 反对系统字体/Inter，而 UI 设计文档 §2.3 指定系统栈+Inter）——盲从 Skill 会破坏既有设计系统。
**正方钢人（强约束派）**：① 用户两次点名（1.1、3.4）「允许使用 Skills 重新设计」，这是授权也是期待；② 冲突解法明确：项目文档管「不变式」（浅色、天梯交互、性能红线），Skill 管「突破面」（视觉方向、氛围、层次）——正好对应 frontend-design 的「bold aesthetic direction」方法论；③ 不写进方案，实施时就会退化成普通 Tailwind 微调，结果还是「Low」。
**裁决**：强约束。每个 UI Phase 的 L3 字段里显式标注「Skill: xxx（读 SKILL.md 后执行）」，冲突以项目文档为上位。

## N6 · 统一阶段的验证门禁怎么设计才不会再出现「e2e 断档」？（拷问 Part 3）

**致命追问**：上一轮 P0 逃逸的根因是「改动后仅复跑单测」，这次凭什么保证不重演？
**反方钢人（轻门禁派）**：单测 191/199 + tsc + build 已经三绿，e2e 全量回归耗时且脆弱，可以在发布前一次性补。
**正方钢人（硬门禁派）**：① 审计 §五 明文登记「e2e 回归执行 🟡——本次缺陷即其逃逸实例」——这不是假设风险，是已发生的事故模式；② 本轮改动恰好横跨 middleware/layout/登录态/Header（e2e 覆盖的正是这些）；③ `verification-before-completion` 的原则：证据先于断言。
**裁决**：硬门禁。Part 3 设 G 系列全局门禁（vitest 全量 + tsc + build + e2e 全量 + 浏览器抽查五件套），且 Part 1/2 每个 Phase 收官时**增量跑** G-1/G-2（沿用现有 checklist 惯例），Part 3 收口时全量跑 G-3~G-5。

**收敛判定**：六个节点经追问与双向钢人后无一被推翻，仅修正如上裁决。进入第三轮重构。
