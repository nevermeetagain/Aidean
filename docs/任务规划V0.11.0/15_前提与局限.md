## 二、局限（本轮结论的边界）

1. **静态证据 ≠ 运行态证据**。35 个"缺错误态"的后台文件中仅 2 个（协议/能力矩阵）取得运行态实证；其余标 `部分确认`，其"已修"结论必须在 B11-05 逐页复测后才成立。
2. **审计是一次性快照**。`fx_daily_rates` 0 行、`catalog_snapshot` 0 行属**当前本地库实况**，不代表生产库；生产是否同样 0 行属 `待确认`（本轮不做生产探测，U-3 冻结）。
3. **缺陷判定基于"演示口径"**。DEF-011-02（价格 949/1000 免费）之所以是缺陷，前提是"演示数据应覆盖可观测维度"；若产品定位就是"全免费演示"，则该条降级为需求问题。
4. **组件一致性只做热区**。149 处裸 `<button>` 中本轮仅迁移混用最严重者，风格统一在 B11-04b 之后**仍不完整**，不得宣称"全站组件已规范化"。
5. **401 治理不触碰契约**。B11-06 采用客户端收敛；若残余红字来自 `auth/me` 的 401 本身，则需 Q-11-02 升格为 A 才能彻底清零。
6. **工时为规划口径**。9 卡 47h 是估算，不含子智能体核验往返与 Fix 闭环时间。（执行期新增 B11-08 后为 **10 卡 51h**）
7. **B11-08 的“已闭环”只覆盖本机 dev 口径**。生产容器内调度链（`Dockerfile` 无 `COPY scripts`、镜像 runner 无 tsx）**未取证也未修复**，已单列 RK-11-07；因此 DEF-011-11 的结论文本必须带此限定，不得写成“调度已全面恢复正常”。
8. **用户可见层只实证了「历史」Dialog 一处**。DEF-011-12 的“修复前恒显示暂无执行记录”**未做缺陷态 UI 截图**（不愿在热更新环境下临时改源文件）；该症状由三证拼接而非直接观察：`ScriptsManager.tsx:224` 调该端点 + 运行态 `total=0`（而 DB=1，持久载体为 `e2e011b.txt` 行8）+ `AdminDataTable` 在 `rows=[]` 时渲染 `emptyText`。同理，DEF-011-11 在 UI「触发」按钮上的失败症状也未单独取图；其依据是 `execprobe011.txt` ①② 实测 `spawn('npx')` 必 ENOENT 与 `script-executor.ts` 将非零退出记为 `status=2` 的代码口径（拼接结论，非直接观察）。
9. **mtime 在本仓当前不可作为排序证据**。本轮观测到 `2026-10-21 08:58:23–25` 的批量元数据簇同时覆盖了编辑时间相隔数小时的 `executions/route.ts`、新增 spec、`apps/web/package.json` 与 `.scratch/*.mjs`；诱因未取证（`待确认`）。因此本目录所有时序结论一律改用**内容内时间戳**（如 `fetchedAt`、`lastRunAt`）排序；若后续需重现事故时间线，mtime 不能单独定案。
10. **DEF-011-13/14 只取证到“点”，未遍历“面”**。信封边界只实测了 3 个出口（405/404/不存在 id）而非全 163 条路由；26 条缺 GET 的单资源路由只核了清单未逐个试其消费方是否真需单资源读取；barrel 拆分的 tree-shaking/bundle 收益未测量。因此不得据此断言“全站 API 客户端均会因空体 405 而炸”。
11. **DEF-011-15 同类面只做了抽样实测**：全仓只真跑 4 个入口（已修端点作对照组 + `audit-logs` + `tier-mappings` + `protocols`），其余靠静态扫描分档（**12/3/0（修前）→ 12/3/1（修后）**，其中“已守卫 1”仅指本卡新修的 `executions`，**修前该档为 0**）。而扫描器的命中条件（同一行同时出现 `parseInt(` 与 `searchParams`）已知存在两类误差：把靠 `\|\|` 兜底的端点误报为高危（`protocols` 实测 200），以及漏检“先把 `url.searchParams` 赋给别名变量再取用”的写法。因此 **12/3/1 是待查模式清单，不是缺陷数，不得当作穷尽**；反向自检（已修文件因改用 `toInt()` 而不再命中）只能证明扫描器不是“全报”，不能证明它无漏；本轮已补**跨行别名盲区交叉核对**（`.scratch/u2-blind.txt`：全仓仅本端点 1 文件使用别名写法），因此该扫描器已知的两类误差均已量化，但**仍不构成穷尽证明**。
12. **M1 加固未取“本端点的修前值”**：`scripts/[id]/executions` 在加固前对 `?page=abc` 会送 NaN 这一判定来自**读码 + 兄弟端点同构写法已实测 500**（`t9-sibling.txt`），而非在同一端点上取到过 500 前值（文件已改，不可回溯）。故本项的证据形态是「单测断言（第 7 例 `Number.isFinite`）+ 生产口径运行态 200」，属拼接结论而非前后对照，不得写成“已实测修复前 500”；本轮收口时已**补做并落盘变异检验**（正规载体 `.scratch/u3-mutation.txt`：`PATTERN_HIT p1=True p2=True`、`GUARD_CALLS_LEFT=0`、**`MUT_TEST_EXIT=1`**、`Tests 1 failed \| 6 passed (7)`、`AssertionError: expected NaN to be +0`，随后按 SHA 还原 `MATCH=True`；首次尝试的 `u2-mutation.txt` **未写入退出码且中文用例名乱码**，只能作历史痕迹、不得当凭证，第 17 次证伪），所以该结论现同时有“断言有效性”的直接证据，但**“修前该端点实测 500”这一点仍未取证**，本局限仅缩小而未消除。
13. **fx CLI 的参数解析没有 vitest 单测**（第四轮子智能体 Minor-4，按「登记而非扩范围」处置）：`scripts/crawl/fx_daily.ts` 的 `--rate`（包括 `--rate=值` 写法）、非法值、缺值、越界、未知参数等行为**只有脚本级取证**（**更正，第 29 次证伪，由第五轮子智能体发现**：本行原写为「`--rate` / `-r`」，但源码只认 `--rate` / `--rate=` / `--dry-run` / `--help` / `-h`——`fx_daily.ts` L239–266 无 `-r` 分支、全文件引号包起的选项字面量按正则 `["']-{1,2}[A-Za-z][\w-]*["']` 命中 7 处、去重后为 `"--rate"` / `"--dry-run"` / `"--help"` / `"-h"` 四个（`"--rate="` 因尾部等号不入该正则，L243/L248/L257 确有），其中无 `-r`，`scripts/` 全域 27 个 `.ts/.js/.mjs` 对 `"-r"` / `'-r'` **0 命中**，取证脚本 `fxcli011d.txt` 十七行命令行样本里含 `-r` 者 **=0**（正控：同一写法对 `"--rate"` 命中 1 处，`CONTROL_FAILED=0`，证明零不是工具假零）——载体 `.scratch/u12-noDashR.txt`（487 B，mtime 15:56:08，尾行 `VERDICT=NO_SHORT_R`）。所以 `-r` 是凭空写入的短选项，属“把同类工具的惯例当成被测对象的行为”）。九例落盘于 `.scratch/fxcli011d.txt`（两种形式 exit=0 且 `source=manual`；非法值/缺值/越界/未知参数 exit=2；并实测出「混用两种形式时后一个参数被静默忽略」这一软点）。仓内 `scripts/crawl/__tests__/fx_daily.spec.ts` 覆盖的是**取数与入库路径**，未覆盖 CLI 解析分支（本轮定向复跑该文件得 30 例 / exit=0，仍不含解析分支用例）。**风险**：日后重构参数解析时不会被单测拦住。**为何不在收口阶段补**：新增用例会改变全量用例数（现值见 `25_` §9.2 全量行）并使已落盘的七项读数全部作废，需重跑 build / gates / vitest 全量（按 `25_` §9.2 「注释级变更即令读数失效」口径），代价高于收益——转下一轮，建议并入任一后续涉及 fx 链路的卡（如 B11-02）。
