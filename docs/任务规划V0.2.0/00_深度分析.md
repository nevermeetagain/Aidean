### Why（原因）
- 需求未实现的**直接原因**：开发按台账驱动，需求文档 v1.14 之后的 MUST（§3.6 限时优惠、§3.9 开关）没有进入任何 spec；台账只记「做了什么」，没有反向「需求→是否实现」的视图——这正是本轮「统一规划体系」要补的**根本原因**。
- 计价缺陷根因：采集与种子引入多币种多单位价格（D5 修复只补了 billingUnit 字段持久化），但计费引擎早于该字段设计，从未消费它；展示侧另写了 provider-pricing 换算但声明不参与扣费——口径分裂在两处。
- 端口结论错误根因：V0.1.0 只看本仓引用面（e2e/脚本 3333），未核验外部仓；本轮读取 BotHot AGENTS.md 后推翻。
- 只改表面的风险：若只把 seed 3200 改为 3333（V0.1.0 TASK-008），BotHot 登录会被白名单拒绝。

## 第二轮 · 苏格拉底追问（关键结论）

**结论 A：「二次写价必然 P2002」**
1. 凭什么？PGlite 上的 SQL 复现。2. 证据来源：EVD-BASELINE-V2/pglite-repro-p2002.txt。3. 是否最新代码？迁移目录与 writer 源码均取自 59e83dd。4. 反证？PGlite 不是真 PG16 服务器、跳过了 pgcrypto；但唯一索引语义属 PG 核心，与扩展无关。5. 表象/根因？根因是「全列唯一 + 历史行 is_current=false 重复」，非并发。6. 遗漏？Prisma 未包事务——真实代码第 2 次在 updateMany 即失败，结论同。7. 前提：writer 被调用且模型已有一条历史行。8. 前提不成立（从未二次同步）则缺陷潜伏但仍阻断限时优惠。9. 需额外验证：TASK-010 真 PG16 固化。10. 足以支持「进入 S1」，不足以宣布「已修复」。

**结论 B：「网关对 USD 价格少收」**
1–2. 读码：service.ts 不读币种。3. 最新代码：是。4. 反证：seed 的 USD 数值可能本身就是人民币（字段写错）——**未排除**。5. 可能把「数据录入口径」误判为「计费缺陷」。7. 前提：USD 行确为美元原价。9. 需 TASK-049 盘点 + 人工抽样。10. **不足以**直接改扣费 → TASK-048 设为条件卡（U-15）。

**结论 C：「seed 3200 不是缺陷」**
1–2. BotHot AGENTS.md 端口表 + BotHot CI 注释。3. 外部仓 HEAD 13acacc（2026-10-14）。4. 反证：本仓 e2e/单测期望 3333——说明 AideanBot 曾用 3333，两者并不矛盾（同一 client 多回调）。8. 若 BotHot 实际不走主平台 SSO，则 3200 可能冗余——但 BotHot CI 明言已登记。10. 足以推翻 V0.1.0 TASK-008，不足以决定是否补 3333（P-2）。

**结论 D：「需求 83 条已穷尽」**
4. 反证：功能设计文档、界面交互文档中可能还有未进入需求文档的细粒度交互规格。处理：本轮把它们视为「设计」而非「需求」，仅当台账/大纲把其中条目登记为未完成时才入 RTM——**局限**登记于 15。
