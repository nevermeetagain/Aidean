# 00 · 深度分析（5W1H → 苏格拉底追问 → 双向钢人 → 终稿）

> 版本: v1.1 | 更新: 2026-10-23 | 变更: 重分工：Hark 8 卡 / 33h（只做架构师级核心），外部助手 A 18 卡 / 47.5h、B 10 卡 / 46h

> 方法：「辩证统一」——每个结论同时写出成立的证据、推翻它的最强理由、以及它在什么前提下失效。证据锚点指向 `02_事实基线.md`（D-xx / §二）与 `03a_统一需求追溯矩阵.md`（REQ-xx）。

## 一、第一轮：5W1H 发散

### What：客观现状
1. **V0.11 代码已全部合并，但收口没做。** B11-01…11、P0、UX-01/UX-FIX、SEC 均在 main（v011_status §1）；B11-RTM（追溯回写、全量 e2e、docker build、`pnpm gates`）未开工，V0.11 README 停在 10-21 的 v0.28，与代码多处矛盾（D-08、D-09）。
2. **门禁「绿」有盲区。** 默认测试跑法跳过 DB 集成测，因此 `effective-price.int.spec.ts` 自 491481c 起就是红的而无人察觉（§二）；全量 e2e 在 V0.11 与 Next 升级后均无读数；CI Actions 0 次运行（U-25=本地复刻）。
3. **需求面：150 条中 101 已实现、22 部分、9 未实现、10 待澄清、7 冻结、1 取消**（03a）。MUST 70 条中 58 已实现、7 部分、5 冻结、**0 未实现**——没有「核心功能缺失」，缺的是 **7 条 MUST 的最后一公里**：监控每日自动采集（M-002/M-009）、多源可调用对外（M-006）、AA 署名（M-015）、3333 端口用例（C-006）、文档拆分（C-008）、追溯表（L-009）。
4. **「建了没接上」仍是主要缺陷形态**：监控 run-now 只占锁无消费者（M-011）；cadenceCron 无读取方；可靠性映射函数写好了但落库缺唯一键（M-008，`llmtest-observations.ts` 头注释自述）；`uiStore.lang` 无读取方（D-05）；Favorite 表与 API 都有，Dock 却只有对比篮（N-009）。
5. **账户安全缺口**：无改密 / 找回密码（N-012）；会话校验不比对 tokenVersion（NF-011），封禁或改密后旧 access 仍可用到 15 分钟到期。
6. **视觉一致性靠「重定义 slate」维持**：UX-FIX-D 把对比度降到 0 的手段是改写 slate-400/500 的值（D-17），硬编码色板 2011 处仍在；三主题切换时状态色不跟随；用户端无五态外壳；组件测试为 0。
7. **工程隐患**：middleware 经 `auth/constants.ts` 拉入 Prisma（Edge 警告，163 kB）；20 个被读取的环境变量没有示例；packages/ui 的 tailwind（^3.4）与 vitest（^3.2）与 apps/web 不同大版本。

### Why：深层原因
- **收口被跳过的原因**是执行组织方式：V0.11 中途从两助手改为单助手，队列以「卡合并」为终点，RTM 卡排在最后且不产生用户可见变化，于是最先被省略。根因不是人，是**「完成定义」没有把收口写成门禁**——本版把 T120-36 设为所有卡的汇点，并让 `check-docs-facts` 读矩阵本身（T120-06）。
- **「建了没接上」反复出现**的原因：卡面以「模块交付」为验收单位（collector 写好、端点返回 202 即通过），没有「端到端可演示行为」的验收句。本版按垂直切片写验收（例：「点立即运行后 ≤1 个节拍内真实采集一次」）。
- **视觉漂移**的原因：令牌体系先天双轨（新旧命名并存），组件没有可强制的守卫，修复只能在值层面打补丁。只修值，下一个新组件仍会写 `text-slate-500`。
- **测试盲区**的原因：集成测与 e2e 需要外部资源（PG、浏览器），默认命令不跑；没有一个「全部门禁」入口脚本。

### Where / When：边界与时序
- 范围：`apps/web`、`packages/{shared,ui}`、`scripts/`、`e2e/`、`docs/`。**不在范围**：子平台仓库、生产部署（U-3，仅 RK-11-07 局部解冻）、产品截图（U-4）、微信登录与在线支付（U-11）。
- 端口：Aidean 本地 dev/e2e 固定 **3000**（3000–3100 区间内）；测试库 PG 用非业务端口（55432），不占用用户访问端口区间；子平台回调以 seed 的 **3200** 为准，**3333 不再保留**（P-1/P-2=A）。
- 时序硬约束：契约（T120-10）先于一切依赖新 schema 的卡；三个迁移严格按版本号串行（11→12→13）；设计令牌（T120-25）先于任何颜色迁移；收口（T120-36）最后。
- 时间节点：本规划在 APPROVE 之前不改业务代码；外部助手的 S12-0/S12-1 与 Hark 的 T120-10/02/25 可在批准后同日开工。

### Who：主体与责任
- **Hark（8 张 / 33h，只做 5 年以上架构师级别、错了会伤全局的部分）**：T120-10 契约与监控执行模型 ADR；T120-12 运行请求并发消费与防重入；T120-13 可靠性去重迁移与幂等唯一键；T120-18 会话 tokenVersion 校验；T120-20 找回密码防枚举与限流；T120-23 自定义渠道 SSRF 探测；T120-25 语义令牌与 Tailwind 版本统一；T120-26 五态外壳上移 @aidean/ui。另负责外部助手 B 的 UI 卡设计验收与核心卡代码审查（不写入）。
- **外部助手 A（18 张 / 47.5h）**：门禁复绿、e2e、docker、环境变量、文档与追溯、AA 署名、轻提示、组件测基建、性能复测、单测/e2e/组件测、收口、条件卡。
- **外部助手 B（10 张 / 46h）**：middleware 拆分、监控脚本注册调度、改密 API、可靠性读侧与展示、监控后台页、改密/找回页、Dock、codemod 与用户端/管理端/非 admin 迁移；UI 按 `03_solution/design/DESIGN-00x` 实现，推送前过 Hark 设计验收。
- **用户**：Q-12-01（BLOCKING，条款放行）与 Q-12-02…08 的裁决；APPROVE；提供有 Docker 的机器（T120-04）。
- **独立验证者**：子智能体，只看 diff + 运行结果，输出 PASS / FAIL / UNKNOWN。

### How：实现路径
1. 先让「绿」名副其实：DB 集成测复绿并有 `test:int` 入口 → 全量 e2e → docker 实测（S12-0）。
2. 真相归一：追溯矩阵再生成并成为 facts 的数据源；V0.11 文档收口（S12-1）。
3. 核心闭环用垂直切片推进：监控调度（S12-2）→ 可靠性（S12-3）→ 合规展示（S12-4）→ 账户安全（S12-5）→ 用户端体验（S12-6）。
4. 设计系统一次性收敛：令牌 → 五态外壳上移 → codemod + 守卫 → 两端批量迁移 → 性能（S12-7）。
5. 测试补齐与收口（S12-8）：同一 HEAD 一次性取全部读数。

## 二、第二轮：苏格拉底追问（每个关键结论至少一问）

**Q1「MUST 0 未实现」凭什么成立？** 证据是 03a 的逐条代码锚点。反证可能：RTM 子智能体只读代码不跑运行态，「已实现」可能是「代码存在但链路断」（正是 V0.11 的主要缺陷形态）。→ 修正：本结论只表述为「**代码层面** MUST 无完全缺失」，运行态由 T120-03 全量 e2e 与 T120-36 收口验证；不得据此宣布「核心功能完成」。

**Q2「门禁有盲区」是否夸大？** 支持：集成测红了且默认不跑是实测（§二）。反驳：CI 的 verify job 可能配了 DB。核查：`ci.yml` 有 e2e-skeleton job，但 Actions 从未运行（U-25），所以无论配置如何都没有读数。→ 结论成立，前提是 U-25 维持本地复刻。

**Q3 监控「只占锁无消费者」是否误读？** 支持：`run/route.ts` 头注释明写「本端点只受理并占锁；实际采集由调度侧执行」，全仓无 `lock:monitor` 读取方（RTM M-011 证据）。反驳：调度侧可能按 lastRunAt 自行轮询所有源，等价于「会被执行」。核查：seed 中 ScheduledScript 未登记 monitor_catalogs（`seed.ts:307-324`），调度侧根本不运行它。→ 成立，且比原描述更重：不仅「立即运行」无效，**定时也不运行**。

**Q4 为什么 run-now 要新建意图表而不是复用 Redis 锁 + nextRunAt=now？** 支持新表：可审计、可查询状态（后台需要显示 pending→done）、Redis 不可用时（现口径 fail-open）仍有 DB 级防重入。反驳：多一张表、多一个迁移，复杂度上升；改 `ScheduledScript.nextRunAt=now` 零迁移即可触发。裁决：nextRunAt 只能触发「全部源」而不能指定单源，且无法回答「我点的那次跑完没」——不满足 M-011「手动触发一次运行」的可验证句。→ 采用意图表，复杂度用部分唯一索引与 30 分钟僵死回收控制。

**Q5 tokenVersion 比对会不会拖慢每个请求？** 支持担忧：requireUserApi 已回库查 status/deletedAt，再加字段不增加往返（同一行投影）；若加 Redis 缓存反而多一跳。→ 修正卡面：优先在**既有回库查询中加投影**，Redis 缓存仅在该查询被证明为热点时启用；验收句改为「无新增 DB 往返」。（T120-18 已按此写。）

**Q6 SSRF 防护会不会误杀合法渠道？** 反驳：部分用户的中转站就在内网。立场：主平台服务端代替用户向任意地址发请求，内网可达等于把主平台变成跳板，风险远大于便利；内网渠道仍可**保存**，只是不做服务端探测（返回 30005 并提示）。→ 成立，并在 DESIGN-004 写明豁免策略：无。

**Q7 设计系统收敛是不是「为了好看」而扩大范围？** 反驳最强：UX-FIX 已把对比度降到 0，再迁移 2011 处是高成本低收益。支持：①三主题切换时状态色不跟随是**功能缺陷**（UI设计文档 §2.2 要求主题切换）；②值层面重定义 slate 会让任何新组件重新引入对比度问题，守卫无法拦截；③用户端无五态外壳导致 UX-02 同类「失败显示为空」可复发。→ 成立，但范围收紧：codemod 驱动 + 守卫兜底，不做逐像素重设计；视觉差异仅限预期并截图评审。

**Q8 i18n 是需求还是遗留？** 界面交互文档写了中/英切换，ADR-0006（已接受）明确不做。ADR 的效力高于设计文档的历史描述。→ 不在本版实施，Q-12-02 建议 A（删除未用状态 + 改文档），若用户要国际化须新 ADR 推翻 0006。

**Q9 Hark 该做多少？**（v1.1 修订）首版让 Hark 承担 18 卡 / 78h（62%），把「带设计判断的实现」也算成核心，这违背了用户 10-22 与 10-23 的明确口径：核心 = 必须 5 年以上架构师 / 开发者才能高效完成、对项目有重大影响的部分；2–3 年开发者能做的全部下放。按此重分：Hark 只保留 8 张（契约、并发消费、去重迁移、会话安全、找回安全、SSRF、设计令牌、共享五态外壳），33h，占 26%；其余 28 张由外部助手 A/B 两条互不相交的车道承担，UI 设计判断以 DESIGN 文档冻结 + Hark 验收的方式保留。Q-12-09 随之关闭。

## 三、第三轮：双向钢人论证（4 项关键判断）

### 判断 A：本版先做 S12-0（门禁复绿）再做功能
- **支持**：没有可信基线，任何功能卡的「测试通过」都不可信；集成测红、e2e 无读数是实测事实；成本低（≈9.5h，外部助手可并行）。
- **反对**：用户要的是「核心功能与测试」，先做基建会推迟可见进展。
- **处置**：S12-0 全部交外部助手且与 Hark 的 T120-10/02/25 同日并行，不占关键路径。反对意见被时序安排消解。

### 判断 B：契约增量只新增 1 个错误码
- **支持**：复用既有码能保持前端错误映射稳定；改密旧密错与重置码错都用 10003 能统一防枚举语义。
- **反对**：错误码复用会让日志难以区分失败原因。
- **处置**：区分靠审计 action 与结构化日志字段（`reason`），不靠对外错误码。反对意见部分成立 → DESIGN-002 要求日志带 reason。

### 判断 C：可靠性迁移先去重再建唯一索引
- **支持**：没有唯一键，`createMany` 重复运行会产生重复行，读侧统计失真。
- **反对**：去重是破坏性操作。
- **处置**：卡面设熔断——去重将删除 >1000 行时停下报用户；保留最新一行（按 created_at）。生产库现状 `证据不足`（沙箱无生产数据），故熔断是必要条件。

### 判断 D：设计令牌版本对齐（tailwind 3→4 于 packages/ui）
- **支持**：同一 monorepo 两个 Tailwind 大版本，令牌无法单源。
- **反对**：packages/ui 组件可能依赖 v3 行为，升级会连锁失败。
- **处置**：卡面写入回退条件（>20 失败即保留差异并在 ADR 记录），并让 T120-30（组件测试）在 T120-26 之前就位以捕获回归。

## 四、终稿（带前提与局限）

**结论**：V0.12.0 的主题是「**收口真绿 + 七条 MUST 最后一公里 + 账户安全 + 设计系统收敛**」。共 9 个切片、36 张卡（2 张条件卡）、126.5h，关键路径 45h（T120-10→11→12→13→14→27→29→31→34→36）。第一刀为 S12-0 步行骨架：让 HEAD 上 DB 集成测、全量 e2e、docker 三项读数首次全部存在且为绿。

**成立前提**：①APPROVE 获批；②Q-12-01 以外的待裁决项按建议默认执行或在开工前改判；③外部助手遵守所有权矩阵与熔断；④有一台可运行 Docker 的机器。

**局限**：运行态与视觉结论来自代码与既有 EVD，本规划未重跑浏览器；性能目标是相对 15.5.28 首测值的相对目标，首测前不可量化；子平台仓库不在核查范围；工时为单人专注估算。

**未验证项**：容器内调度、生产库可靠性表的重复数据规模、生产 SMTP 可用性、Windows 侧 `pnpm gates`。

**是否允许进入下一阶段**：允许进入 APPROVE；IMPLEMENT 须待用户批准。
