## 一、执行摘要

### 1.1 核心共识（两个评审视角 + 9 份参考文档交叉验证）

**✅ 架构方向正确：**

1. **Hub-and-Spoke 适合单人开发**：统一身份/计费/模型配置极大简化一致性保证，避免分布式事务。大多数 SaaS 生态都是 Hub 模式（AWS IAM、Google Workspace）。【高置信度，6+ 份文档一致认可】
2. **自建 OIDC 在当前需求下可行**：授权码流 + PKCE + refresh token 轮换已实现（7 端点），Keycloak 杀鸡用牛刀且增加 Java 运维负担。ADR-0003/0005 已锁定自研路线。【高置信度，ADR 铁律】
3. **主平台唯一账本 + 两阶段扣费设计正确**：hold → capture → void 精确处理长任务，ledger append-only 不可变审计，requestId 幂等消除重复扣费。代码已实现 Wallet.lockVersion 乐观锁。【高置信度，代码实证】
4. **契约 SSOT + 双语言包 + CI 门禁**：保证接口一致性，packages/shared 已有 Zod schema 雏形可演化为 contracts/。【高置信度，代码实证】

**❌ 必须修改的高风险项：**

1. **事件 Outbox 完全未实现**（设计-代码差距 F1）：设计声称 PG Outbox + HMAC Webhook + 7 事件类型，Prisma 55+ 模型中无 outbox 表，全代码库无 HMAC 事件签名代码。**阻塞跨平台事件通信**。
2. **AideanBot 网关未接入**（F3）：设计声称"已接入网关"，实际直连 8 个 provider。**违反 D10 网关统一铁律**。
3. **Hub 单点故障无高可用方案**：主平台 crash 导致所有子平台写路径中断。需补充多实例 + 负载均衡。
4. **Fleet "零依赖"铁律与"走网关计费"根本冲突**：ADR-026 禁 Redis/MySQL，但 D8 要求模型调用全量走主平台网关。需重新定义"零依赖"边界。
5. **性能目标完全缺失**：方案口头承诺"高性能"，但无量化 SLA、无压测计划、无扩容阈值。

**⚠️ 需澄清的盲区：**

1. internal API 是透传还是编排？（影响主平台代码膨胀）
2. BotHot KB 是否支持内容 hash + 版本留痕？（影响溯源层设计）
3. 当前主平台 usage_logs 表规模和写入 TPS？（影响性能规划）
4. OIDC IdP 是否实现 SSO session？（影响一键登录体验）
5. AideanCompany vs AideanFleet 编排分工？（两个平行 fleet 系统）

## 四、总体融合架构

### 4.1 拓扑：Hub-and-Spoke + 事件契约主干

```
                    ┌──────────────────────────────────────────────┐
                    │           Aidean 主平台 :3000                │
                    │  ┌─────────┐  ┌──────────┐  ┌────────────┐  │
                    │  │OIDC IdP │  │ 计费账本  │  │ 模型网关    │  │
                    │  │(7端点)  │  │hold/cap  │  │/gateway/chat│  │
                    │  └────┬────┘  └────┬─────┘  └─────┬──────┘  │
                    │  ┌────┴────────────┴───────────────┴──────┐  │
                    │  │  生态编排器(DAG+预算门+审批门) 事件网关 │  │
                    │  │  (Fleet Control Plane 嵌入)  HMAC签名   │  │
                    │  └────────────────────────────────────────┘  │
                    └──┬──────────┬──────────┬──────────┬─────────┘
            OIDC授权码流 │ 计量/预留 │ 网关调用 │ 事件(信封+HMAC)
           ┌────────────┼──────────┼──────────┼──────────┐
           │            │          │          │          │
      BotHot       AideanBot    Thesis     Fleet
      :3200        :3333        :3400      :3100
      采集雷达      对话/通知     生产交付    DAG编排/查证
      10渠道推送    通道         查重/写作   8执行器+reviewer
```

### 4.2 六层架构定义

| 层 | 职责 | 组件 | 数据流方向 |
|:---:|------|------|------------|
| **T0 枢纽层** | 唯一身份/计费/网关/模型配置权威 | Aidean 主平台 | 双向（授权↓ 计量↑） |
| **T1 编排层** | 跨平台 DAG 调度/重试/断点续跑/预算门/审批门 | Fleet Control Plane | 下发 TaskPack ↑ 回收 Evidence |
| **T2 能力层** | 采集/推送/写作/分析/查重/查证 | BotHot + AideanBot + Thesis + Fleet | 接收任务 ↑ 返回产物 |
| **T3 知识层** | 摄取/混合检索/快照溯源 | 一期：BotHot KB；二期：独立知识服务 | 查询↓ 结果↑ |
| **T4 身份计费层** | OIDC + 网关代理 + BalanceHold | Aidean IdP + Gateway | 授权码流↓ JWKS 验签↑ |
| **T5 数据层** | 各平台自有 PG + 统一溯源 + 事件日志 | 各仓库独立数据库 | 事件 Outbox → Webhook |

### 4.3 控制面 vs 数据面分离

| 维度 | 控制面（Control Plane） | 数据面（Data Plane） |
|------|------------------------|---------------------|
| 身份 | OIDC 授权码流 + JWKS 验签 | 各子平台 Session（短期，不持久化余额） |
| 计费 | 主平台 wallet + BalanceHold | 子平台经网关调用，计量回传 |
| 模型 | UserTierMapping + ModelProfile | 子平台零模型配置，全走网关 |
| 编排 | Fleet DAG + 预算门 | 各子平台执行体接收 TaskPack |
| 审计 | 主平台 UsageLog + events.jsonl | 子平台本地日志 → 事件回传 |
| 数据 | 不存子平台业务数据 | 各子=平台自有 PG，独立数据库 |

## 五、关键设计决策（经钢人论证幸存）

> 每个决策均经过：正方论证 → 反方钢人 → 苏格拉底追问 → 代码验证 → 幸存/修正/否决

### D1：Hub-and-Spoke 拓扑 — Aidean 为唯一身份/计费/网关锚点

| 维度 | 内容 |
|------|------|
| **决策** | Aidean 主平台为唯一 Hub，所有子平台为 Spoke |
| **支持证据** | BotHot 已实践 `sub` 锚定 + 余额实时查；ADR-0003 铁律 1-5；SSO 指南 v1.4 |
| **反对/风险** | Hub 单点故障 → 全生态登录/计费不可用 |
| **结论** | **维持**。补强：JWKS 缓存宽限（kid 双活已落地）+ 多副本部署 + 健康探针 + 降级模式（网关不可用时子平台只读） |
| **钢人论证** | 反方："应用 Kafka 事件溯源去中心化" → 正方："6 平台规模不需要 Kafka 运维税，PG Outbox + Webhook 足够；ADR-0003 已锁自研路线" |
| **苏格拉底追问** | Q: "Hub 不可用时子平台能否继续服务已登录用户？" A: 可——JWKS 缓存宽限 5 分钟，已登录用户继续使用；新登录不可用。Q: "降级模式下计费如何处理？" A: 子平台本地缓冲扣费记录，Hub 恢复后批量回放（需实现 LocalChargeBuffer）。 |

### D2：Fleet 作为跨平台 DAG 编排器

| 维度 | 内容 |
|------|------|
| **决策** | Fleet 扩展 HTTP 执行体适配器，成为生态级编排器 |
| **支持证据** | Fleet DAG/dispatcher/reviewer 天然适配；10 状态机已覆盖 retry/skip/timeout/budget_gate |
| **反对/风险** | Fleet 零依赖铁律（SQLite + JSONL）被打破 |
| **结论** | **成立**。出站 HTTP 不引入外部服务依赖（只是新增一种 Executor），双模式：自备池（本地 Agent）+ 走网关（云端模型）。SQLite 保留为控制面状态 |
| **实现** | 新增 `HttpExecutor`：`TaskPack → HTTP POST → 子平台 /api/v1/internal/fleet/task` → 回调 `Evidence`；子平台需实现 internal task 接收端点 |
| **苏格拉底追问** | Q: "AideanCompany 也有 fleet（1973 .py 文件），谁是唯一编排器？" A: 需明确分工——AideanFleet = 跨平台编排器（Control Plane），AideanCompany fleet = 平台内任务执行器（Data Plane）。Q: "Fleet 的 10 状态是 1 个状态机的 10 状态，不是 10 个状态机——这是否影响扩展性？" A: 不影响——单状态机足够表达任务生命周期，扩展靠新增 Executor 类型而非状态机。 |

### D3：事件基础设施 — PG Outbox + HMAC Webhook（非 Redis Streams / Kafka）

| 维度 | 内容 |
|------|------|
| **决策** | 事件传递用 PostgreSQL Outbox 表 + HMAC 签名 Webhook |
| **支持证据** | Claude + ChatGPT 双方一致推荐；主平台已有 PG；6 平台事件量 < 10K/day |
| **反对/风险** | PG Outbox 轮询延迟（秒级）；无事件回溯总线 |
| **结论** | **维持**。补强：Outbox 轮询间隔 2s（可配）；Webhook 失败指数退避重试（max 5 次）；事件保留 90 天后归档 OBS |
| **⚠️ 代码差距** | **F1: Outbox 完全未实现**。Prisma 55+ 模型中无 outbox 表，全代码库无 HMAC 事件签名代码。**M0 必须首先实现。** |
| **钢人论证** | 反方："Kafka 提供事件回溯和精确一次语义" → 正方："6 平台不需要 Kafka 运维税（3 broker + ZK/KRaft + 监控）；PG Outbox + 幂等消费者已够；事件回溯用 events.jsonl 归档 OBS 替代" |

### D4：信息采集基座 — BotHot（非 AideanBot）

| 维度 | 内容 |
|------|------|
| **决策** | 以 BotHot 为信息采集与推送基座，AideanBot 逐步退役 |
| **支持证据** | BotHot 是 AideanBot 的升级版；10 渠道 vs AideanBot 单渠道；热点聚簇数据模型已建 |
| **反对/风险** | AideanBot 已接 SSO + 网关（唯一完整接入），BotHot 尚未接网关 |
| **结论** | **成立**。BotHot 复用 AideanBot 的 SSO 接入路径，新增 `bothot-web` client；Phase 2 接入网关 |
| **苏格拉底追问** | Q: "AideanBot 网关实际未接入（F3），是否影响退役决策？" A: 不影响——反而说明 AideanBot 的网关接入是设计声称而非代码现实，退役无实际损失。Q: "BotHot DDD 脚手架是空壳（F5），是否影响作为基座？" A: 需在 M0 填充 DDD 模块骨架，但不影响核心功能（10 渠道推送已实现）。 |

### D5：AideanWiki 延期 — 知识适配器模式

| 维度 | 内容 |
|------|------|

### D6：Thesis 身份替换 — 删除自建 JWT，接入主平台 OIDC

## 六、对抗性审查 — 8 个最可能失败点

> 红队视角：假设我是攻击者/竞争者/悲观主义者，找出方案最可能在何处崩塌。

### F1：Hub 单点故障 → 全生态不可用

| 维度 | 内容 |
|------|------|
| **失败场景** | 主平台数据库 crash 或 OOM → 所有子平台无法登录、无法扣费、无法调用模型 |
| **影响范围** | 全生态写路径中断（登录/扣费/溯源注册/模型调用）；读路径部分可用（JWKS 缓存宽限 5 分钟） |
| **概率** | 中（单实例 PG + 单 Next.js 进程；无副本、无负载均衡） |
| **严重度** | **致命** |
| **缓解措施** | ① PG 主从复制 + 自动故障转移 ② Next.js 多实例 + Nginx 负载均衡 ③ 子平台 LocalChargeBuffer（Hub 恢复后批量回放） ④ 健康探针 + PagerDuty 告警 |
| **残余风险** | 主从切换 RPO > 0（可能丢失最近几秒扣费记录）→ 幂等消费者 + 对账补偿 |

### F2：事件 Outbox 积压 → 跨平台任务卡死

| 维度 | 内容 |
|------|------|
| **失败场景** | Outbox 轮询积压（大量任务同时完成）→ 子平台长时间收不到事件 → DAG 超时 |
| **影响范围** | 跨平台编排链路卡死；单平台内功能不受影响 |
| **概率** | 中（PG 轮询无背压；高并发时 Outbox 表膨胀） |
| **严重度** | 高 |
| **缓解措施** | ① Outbox 分区轮询（按 event_type 分组并行处理） ② 批量推送（一次轮询取 100 条） ③ 超时告警（Outbox 中 > 5 分钟未投递的事件告警） ④ 定期归档（已投递事件 1 小时后移至 OBS） |
| **⚠️ 前置条件** | **F1: Outbox 完全未实现**，需 M0 首先实现 |

### F3：Fleet 零依赖铁律被打破 → 架构腐化

| 维度 | 内容 |
|------|------|
| **失败场景** | Fleet 接入网关后逐步引入 Redis/PG 依赖 → 零依赖铁律名存实亡 → 运维复杂度飙升 |
| **影响范围** | Fleet 从"可独立部署的轻量编排器"退化为"需要完整基础设施的重服务" |
| **概率** | 中高（"只是加一个 HTTP 调用"的滑坡效应） |
| **严重度** | 中 |
| **缓解措施** | ① 明确定义"零依赖"边界：内核（SQLite + JSONL）零外部服务依赖；适配器层允许 HTTP 出站 ② CI 检查：import 扫描禁止 redis/pydantic-asyncpg 等重依赖 ③ 架构守卫：dependency-cruiser 规则 |

### F4：性能未量化 → "高性能"是空头支票

| 维度 | 内容 |
|------|------|
| **失败场景** | 用户增长后系统变慢，但无基线数据无法定位瓶颈；联合账单查询全表扫描超时 |
| **影响范围** | 用户体验退化；计费查询超时导致功能不可用 |
| **概率** | 高（无压测、无 SLA、无扩容阈值 = 必然发生） |
| **严重度** | 高 |
| **缓解措施** | ① 定义 SLA：P99 网关延迟 < 2s，P99 账单查询 < 500ms，P99 登录 < 1s ② 建立性能基线：M0 结束时压测 ③ 扩容阈值：QPS > 50 时触发自动扩容 ④ 联合账单查询用预聚合表（UsageDailyStat 已存在） |

### F5：溯源断链 → "可溯源"承诺无法兑现

| 维度 | 内容 |
|------|------|
| **失败场景** | Artifact 引用的 Source 已被删除/修改 → 溯源链断裂 → 用户无法回溯来源 |

## 十二、替代架构对比

| 方案 | 描述 | 优点 | 缺点 | 适用场景 | 结论 |
|------|------|------|------|---------|------|
| **A. Hub-and-Spoke（本方案）** | Aidean 唯一 Hub，子平台 Spoke | 简单一致；单点计费；适合单人开发 | Hub SPOF；扩展受 Hub 性能限制 | < 20 子平台 | **采用** |
| B. 事件驱动去中心化 | Kafka 事件总线 + 各平台独立计费 | 无 SPOF；独立演进 | Kafka 运维税；分布式事务复杂；需要 DevOps 团队 | > 50 子平台 + 团队 | 否决（规模不足） |
| C. Service Mesh | Istio + gRPC + 每平台 sidecar | 细粒度流量控制；可观测性 | 极重基础设施；学习曲线陡峭；单人无法运维 | 大团队 + 微服务成熟 | 否决（运维过重） |
| D. 联邦化 | 各平台独立 + OIDC 联邦信任 + 账单对账 | 最大独立性；无 Hub | 用户体验割裂；计费不一致；对账复杂 | 合作伙伴生态 | 否决（用户体验差） |

## 十六、补充能力：AI 市场发现引擎（来自 模型相关信息/ 目录独特洞察）

> **来源**：核心.md（110K）+ from_qwen.md（51K）+ from_glm.md（7K）
> **洞察**：当前方案的 C3"统一网关"只管理已知模型/Provider，但 AI 市场每天有新 Provider/Model 上架。需要**自动发现引擎**而非静态名单。

### 16.1 问题重构

| 旧范式 | 新范式 |
|--------|--------|
| 人工维护 Provider 名单 | 自动发现未知 Provider |
| 采集"已知"状态 | 发现"未知"变化 |
| 扁平模型价格表 | 多维 AI Market Graph |
| 当前状态快照 | 每日变化事件流 |
| 信任网页标题 | HTTP 探针 + SDK 兼容性测试 + 实际调用验证 |

### 16.2 AI Market Graph 数据模型

```
                         AI MARKET
                             │
          ┌──────────────────┼──────────────────┐
          │                  │                  │
        MODEL             PROVIDER          GATEWAY
          │                  │                  │
    ┌─────┼─────┐      ┌─────┼─────┐      ┌─────┼─────┐
    │     │     │      │     │     │      │     │     │
 能力   版本   发布   官方   云厂商 推理   聚合  中转  Relay
    │                   │
    └──────────┬────────┘
               │
        ACCESS ROUTE
               │
    ┌──────────┼──────────┐
    │          │          │
 Protocol     Tool       Plan
    │          │          │
OpenAI      Codex      Coding Plan
Anthropic   Claude     Token Plan
Responses   Cursor     Subscription
```

### 16.3 发现引擎架构（5 层）

| 层 | 职责 | 数据源 | 产出 |
|:---:|------|--------|------|
| **L1 发现层** | 从互联网公开信号中发现新 Candidate | OpenRouter API / models.dev API / HuggingFace API / LiteLLM JSON / arXiv / GitHub Trending / RSS | Candidate 列表（URL + 初步元数据） |
| **L2 验证层** | 对 Candidate 做技术验证，过滤虚假/过时信息 | HTTP 探针 / OpenAPI 解析 / SDK 兼容性测试 / 实际 `GET /v1/models` 调用 | Verified Provider（含真实能力 + 价格 + 协议） |
| **L3 图谱层** | 构建 Model × Provider × Gateway × Protocol × Plan 多维图谱 | L2 产出 + 已有图谱 | AI Market Graph（增量更新） |
| **L4 变化检测层** | 每日 diff 图谱，输出变化事件流 | L3 图谱（今日 vs 昨日） | ChangeEvent 列表（新增模型/价格变动/Provider 下线/...） |
| **L5 情报层** | 生成人类可读的每日市场情报报告 | L4 ChangeEvent + L3 Graph | 每日情报报告（新模型/价格变化/推荐/风险） |

### 16.4 已实测的采集渠道（来自 from_glm.md）

| 优先级 | 渠道 | 接入方式 | 关键能力 | 覆盖范围 | 费用 |
|:---:|------|------|------|------|------|
| ★1 | **OpenRouter** | `GET /api/v1/models` | `created` 时间戳可 diff 今日新增 + 价格 + 上下文 | 460+ 模型 | 免 key |
| ★2 | **Hugging Face** | `GET hf-mirror.com/api/models` | 分钟级新模型流 + downloads/likes 过滤 | 权重发布 | 免 key（需镜像） |
| ★3 | **LiteLLM** | GitHub JSON | ~6000 条模型注册表；diff 新增 key | 几乎所有 API 提供商 | 免费 |
| ★4 | **models.dev** | `GET /api.json` | 225 家提供商、7857 个含价格模型 | 提供商+模型+价格一体 | 免费 |
| ★5 | 各厂商 `GET /v1/models` | OpenAI 兼容端点 | 单一厂商变更 | 按厂商 | 需 key |
| ★6 | **arXiv / HF Daily Papers** | API | 论文先于 API 上架 1-30 天 | 学术界 | 免费 |

## 二十四、from_chatgpt.md 深度补充（explorer-5 详细分析）

### 24.1 Control Plane vs Data Plane 分离（蓝本完全缺失 — 最重要发现）

> **核心主张**："统一治理 ≠ 所有字节流量都必须经过 Hub"

```
Control Plane：认证、授权、计费决策、任务编排
Data Plane：文档、附件、知识检索结果、长流式内容、大批量导出
```

**落地手段**：大对象只交换引用（asset_id, content_hash, URI, download_token / signed URL），不通过 Aidean API 逐字节搬运。

**影响**：直接改变了 Hub 的定位定义 — Aidean 是 Control Plane，不是 Everything Plane。

### 24.2 三类 API 分类法（蓝本缺失）

| API 类型 | 说明 | 示例 |
|----------|------|------|
| Control API | Aidean → Platform（治理指令） | `POST /tasks {"capability": "thesis.generate"}` |
| Capability API | Platform 自己提供能力 | 平台自有端点 |
| Event API | event_id + reference URI | 事件通知 |

> **错误设计**：`POST /thesis/generate-paper`, `POST /fleet/verify-claim`（Hub 变成超级后端）
> **正确设计**：`POST /tasks {"capability": "thesis.generate", "asset_refs": [...]}`（Hub 只做编排）

### 24.3 结构化 Provenance Edge Table（蓝本部分缺失）

```
provenance_edges
  parent_id, child_id, relation, created_at, event_id

provenance_snapshot JSON  ← 用于重建/审计
```

- Edge table：查询；JSON snapshot：重建/审计
- 三种查询模式：`GET /artifact/x`、`GET /artifact/x/lineage?depth=3`、`POST /export/full-lineage`
- 禁止在线 API 无限递归

### 24.4 事件顺序问题与解决方案（蓝本缺失）

> **"至少一次 ≠ 有序"** — 如果 v3 先到，消费者不能倒退到 v2

解决方案：事件携带 `aggregate_id + sequence` 或 `event_version`

### 24.5 "数据不丢失"形式化拆解（蓝本缺失）

| 指标 | 说明 | 示例目标 |
|------|------|---------|
| RPO | Recovery Point Objective | 账本 RPO = 0 |
| RTO | Recovery Time Objective | — |
| Lineage reconstructability | 谱系可重建性 | Provenance RPO ≤ 1min |
| Billing reconstructability | 计费可重建性 | 对象 RPO ≤ 5min |

### 24.6 Gateway 延迟分解（蓝本缺失）

将"P95 附加延迟 < 100ms"拆解为 5 个可测量子指标：

```
gateway-routing latency
provider-selection latency
auth latency
billing-hold latency
SSE first-byte overhead
```

> 否则 `<100ms` 没有验收意义。

### 24.7 跨平台 URI 方案（蓝本缺失）

```
aidean://<platform>/<entity>/<id>@<version>
```

> 不共享数据库，但共享可验证事实引用。

### 24.8 Scope 精确分解（蓝本部分缺失）

```
identity:basic
wallet:read
entitlement:read
model:invoke
asset:register
asset:read
artifact:read
```

> 平台客户端不能因为需要模型调用，就获得整个用户账户控制能力。

### 24.9 Fleet "三重中枢"警告（蓝本缺失）

如果 Fleet 和 Hermes 都膨胀，会形成：

```
Aidean 一个控制面
Fleet 又一个控制面
Hermes 又一个控制面
→ "三重中枢"（系统性风险）
```

**缓解**：Fleet = Execution Plane 严格冻结；Hermes → Worker Adapter → Fleet（保留独立演化）。
