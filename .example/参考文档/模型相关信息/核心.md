你说得对。**上一版的根本错误，不是少列了几个平台，而是把“自动采集系统”误解成了“维护一张人工平台名单”。**

如果系统还需要你告诉它：

> “别忘了硅基流动、华为云、阿里云、302.AI、DeerAPI……”

那这个系统就根本没有完成“发现”的职责。

真正应该解决的是：

> **今天全球有哪些新的模型、哪些新的模型提供商、哪些新的聚合/Gateway/中转站、哪些渠道新增了某模型、哪些价格/套餐/缓存/协议发生变化——即使昨天数据库里完全没有这个平台，也能自己发现它。**

# 🧠 第一轮（发散）：5W1H 穿透问题

## 1. What — 客观现象是什么？

用户想要**系统性地采集"提供商和中转站"层的数据**，而非仅仅是"哪些模型存在"。这是两个不同的数据层：

| 层 | 实体 | 关键数据字段 |
|---|---|---|
| **模型层** | Claude 4.5 Sonnet | 参数量、benchmark、能力标签 |
| **提供商层** | Anthropic 官方 | 官方定价、context window、cache 策略 |
| **聚合/中转层** | OpenRouter、302.AI、无问芯穹、DeerAPI | 转发定价（相对官方的折溢价）、格式兼容性（OpenAI/Anthropic/自有协议）、quota/plan 结构、缓存命中机制、稳定性/SLA |

**致命追问 #1**：这三层数据真的可以用同一个采集策略统一处理吗？

→ **不能**。模型层有标准 API（OpenRouter `/v1/models`），提供商层有官方文档页，中转站层几乎没有公开的标准 API——它们的定价页是 HTML，额度结构是非结构化的 prose，缓存命中率根本不公开，必须分层设计采集策略。

---

## 2. Why — 深层动机是什么？

用户的真实需求不是"知道价格"，而是**做出决策**：

> "我应该选哪个渠道？为什么？在什么条件下换渠道？"

这背后隐藏的是一个**多维度决策矩阵**：

```
决策维度 = f(价格, 格式兼容性, 额度/Quota类型, 缓存收益, 稳定性, 支付方式, 合规性)
```

**致命追问 #2**：采集数据的目的是"看"还是"算"？

→ 如果只是"看"，聚合页面够了。如果是"算"（实际花费、caching 折后价、按工作负载的性价比），就必须把**缓存命中率**和**quota 结构**纳入采集范围——而这两个字段在几乎所有平台都不直接暴露为结构化数据。

**双向钢人论证**：
- **正方**：结构化 API 采集 + 价格 diff 已能覆盖 80% 的决策需求，额度/缓存是二级需求，可手动维护。
- **反方**：Coding Plan 的"5小时滚动窗口"vs"每周额度"的区别，直接决定 agent 夜间任务能否完成；这个差异根本不在任何 `/v1/models` API 里——忽略它会导致"账面便宜、实际跑不通"的系统性误判。

→ **结论**：必须同时采集两类数据：结构化 token 定价 + 非结构化 quota/plan/cache 信息。

---

## 3. Where/When — 边界条件和时间节点

**边界条件**：

| 边界 | 说明 |
|---|---|
| **数据时效性** | LLM API 定价看似简单，实则复杂——2026 年上半年价格已变动两次，每家提供商对输入/输出 token 的定价方式各异，"标题价格"往往与实际账单不符。 |
| **Coding Plan 变动节奏** | 仅过去 12 个月：Cursor 从基于请求的计费切换到了基于积分的计费，再引入使用量乘数分级；Windsurf 两次彻底重构定价，2026 年 3 月用每日配额取代了积分；GitHub Copilot 引入了分级高级请求体系。 |
| **中转站生命周期** | 中转站是高度不稳定的实体：它们依赖官方账号池（含逆向工程渠道），可能随时被封禁或倒闭。证据：某中转站接口已挂。 这意味着"稳定性/存活状态"本身就必须是一个采集字段。 |
| **缓存 TTL 复杂性** | OpenRouter Pricing 字段包含 `InputCacheWrite`（默认 5 分钟缓存写入价格）和 `InputCacheWrite1h`（仅在支持 1 小时扩展缓存 TTL 的提供商存在，如 Anthropic）。 这说明缓存定价本身是多维的，不是一个字段能概括的。 |

**致命追问 #3**：如果一个中转站今天存在、明天消失，我的采集系统应该怎么处理？

→ 需要设计**心跳探活**机制（定时 ping `/v1/models` 或发送一个最小 token 请求），并记录"连续失联天数"，而不是仅记录静态价格。

---

## 4. Who — 涉及的主体分类

现实中的"提供商和中转站"不是一个同质的类别，必须按**上游来源**分层：

```
┌─────────────────────────────────────────────────────┐
│ 一级：原厂官方（One-Party）                          │
│  OpenAI / Anthropic / Google / DeepSeek / Mistral   │
│  → 最权威定价，无溢价，有批处理 API，有官方 SLA      │
├─────────────────────────────────────────────────────┤
│ 二级：云厂商授权转售（Two-Party）                    │
│  AWS Bedrock / Google Vertex / Azure AI Foundry     │
│  → 合规转售，区域端点有约 10% 溢价，但有企业 SLA     │
├─────────────────────────────────────────────────────┤
│ 三级：聚合网关（Multi-Party Aggregators）            │
│  OpenRouter / 无问芯穹(GenStudio) / 302.AI           │
│  → 一个 API Key 多模型；有额外平台费；有自有路由逻辑  │
├─────────────────────────────────────────────────────┤
│ 四级：民间中转站（Relay/Proxy Stations）             │
│  DeerAPI / hao.ai / SudoCode / EiRouter / YKH.AI   │
│  → 通过官方账号池或逆向渠道转发；无官方授权；高风险   │
│  → 价格通常比官方低，但稳定性、数据安全无保障         │
└─────────────────────────────────────────────────────┘
```

**双向钢人论证（关于四级中转站的价值）**：
- **正方**：有人实测，选择价格在人民币 ¥1(进)6(出)/百万 Token 的 GPT 5.6 Sol 中转站，少充点钱也是可行选项。 对于个人开发者或测试场景，性价比极高。
- **反方**：四级中转站无法保证：①数据不被记录/出售；②账号池不被封导致服务中断；③"智商满血"无法被独立验证；④不能用于任何涉及用户隐私的生产环境。

## 5. How — 执行路径（技术实现）

这里是最关键的部分，必须分层设计，不能用单一方案一刀切。

### 5.1 结构化数据采集层（可 API 化）

#### 【A】OpenRouter `/v1/models` — 最核心的结构化源

OpenRouter Pricing API 的字段包含 `Discount`（端点折扣系数，价格 × (1-discount)，0=无折扣，1=免费）、`InputCacheRead`（缓存命中读取单价）、`InputCacheWrite`（缓存写入单价）。

响应体中的 `cache_discount` 字段会告知本次请求节省了多少（缓存收益）。部分提供商（如 Anthropic）对缓存写入有负折扣（写入更贵），但对缓存读取有正折扣（读取更便宜）。

这意味着 OpenRouter 的 `/v1/models` 返回的字段已经是**可计算的缓存经济学模型**，不是只有单价：

```python
# 真实成本计算（含缓存）
effective_input_cost = (
    uncached_tokens * input_price +
    cache_write_tokens * cache_write_price +
    cache_read_tokens * cache_read_price
)
# cache_discount 字段直接从响应中读取
```

**关于 OpenRouter 平台费结构（证据链）**：

OpenRouter 的定价是透明的——你付的是提供商收取的价格加上 5.5% 的便利费；具体地，OpenRouter 在充值金额上收取 5.5%，token 本身无加价。

BYOK（自带 API Key）模式：前 100 万次请求/月免费，之后收取用量的 5% 费用。

OpenRouter 是一个多模型 LLM API 市场：一个 API Key、一个余额，统一访问来自 80+ 提供商的 500+ 模型（OpenAI、Anthropic、Google、Meta、Mistral、DeepSeek 等），含自动路由、故障切换。

OpenRouter 自动透传提供商缓存折扣：Anthropic 模型缓存输入 token 约 90% 折扣，OpenAI 约 50% 折扣。

**缓存命中率的关键机制**：

OpenRouter 的 sticky routing（粘性路由）将后续请求固定到同一提供商，以最大化缓存命中率。在 DeepSeek R1 等模型上，这能使有效定价比基础费率低 60~80%，响应中的 `cached_tokens` 字段可确认每次响应的折扣。

#### 【B】无问芯穹（GenStudio）— 国内合规聚合平台

无问芯穹 GenStudio 自 2026-03-30 起，通过 API 调用的预置大语言模型均按实际 Token 用量后付费结算；不同服务等级对应不同限频与单价。

三个服务等级的核心参数：


- **基础服务**：RPM=12、RPD=300、TPM=12,000
- **高级服务**：RPM=1,200、RPD 不限、TPM=1,200,000
- **企业服务**：自定义，按合同约定


还有**包并发服务**：按槽位数收取月费锁定预算，超出请求可选择自动拒绝或自动回退到按 Token 计费模式。

GenStudio 是 MaaS 平台，支持 OpenAI 兼容的标准化 API 接口；2026-03-30 起已停止基础版 LLM API 免费服务，体验中心（网页端）仍暂不计费，向量嵌入与重排序模型 API 仍暂不收费。

**致命追问 #4**：GenStudio 的计费数据能 API 化采集吗？

→ 官方文档明确：在用量统计页面可查看 API Token 用量，记录时间为北京时间（UTC+8）；用量统计页面**不展示具体费用**。 这意味着费用字段不在公开 API 里，价格信息只能通过爬取"服务列表"页面或订阅官方公告获取。

#### 【C】Coding Plan 层 — 额度结构必须独立采集

月度 Token 配额、滚动提示配额、以及"无限"层（超过高速上限后会降速）这三种方式在定价页面看起来类似，但在真实 Agent 工作负载下的行为完全不同。

有些订阅在聊天和编程之间共享一个配额，专用计划在固定或滚动窗口内计算请求数，而基于积分的计划则根据模型和工作负载扣除用量。

当前市场主流 Coding Plan 的额度结构（证据直接来自 rankllms.com）：


- **GLM Coding Plan Lite**：$18/月，5小时窗口 2,000 积分，每周 10,000 积分，无月度硬上限
- **GLM Coding Plan Pro**：$72/月，5小时窗口 12,000 积分，每周 60,000 积分
- **Alibaba Model Studio Coding Plan Pro**：$50/月，5小时窗口 6,000 请求，每周 45,000 请求，月度 90,000 请求（含 Qwen+GLM+Kimi+MiniMax 多模型）
- **Kimi Code Andante**：约 $7/月，有每周 5 小时编程额度上限


MiniMax Token Plan：$22/$55/$132 三挡，均为每周 Token 窗口，不滚存。

Anthropic Claude Pro：$20/月（年付 $17/月），含 Claude Code 和 Claude Cowork；Max 5x：$100/月，Max 20x：$200/月。

**致命追问 #5**：这些 Coding Plan 数据能自动化采集吗？

→ **几乎不能**。这些数据全部在 HTML 定价页里，没有任何标准 API。这些信息分散在各自独立的账单仪表板中，如果有记录的话。 自动化方案只能是：HTML 爬虫 + 结构化提取 + 人工周期性校验。

### 5.2 中转站层的采集策略

**四级中转站的数据特征**（基于 GitHub 证据链）：

部分中转站已支持 GPT、Claude、xAI Grok 等主流模型，并兼容了 OpenAI、Anthropic 等常用协议与 SDK，还提供模型路由、故障回退、团队管理及完整调用日志。

典型价格示例（2026年）：GPT 5.6 Sol 人民币¥1(进)6(出)/百万 Token，Opus 5 的 CC Max 渠道¥7(进)35(出)/百万 Token。

**致命追问 #6（最核心）**：中转站的"缓存命中率"真的可以采集吗？

→ **不能直接采集**。缓存命中率是运行时数据，取决于：①你自己的请求是否触发了缓存（前缀重复度）；②中转站是否透传了上游的 `cache_discount` 字段；③该中转站的 sticky routing 实现是否正确。唯一可行的方案是：**发送一批已知前缀相同的测试请求，对比响应中的 `cached_tokens` 字段**，自己实测而非采集官方声明。

## 6. What if — 前提改变时的连锁影响

| 前提改变 | 连锁后果 |
|---|---|
| 若 OpenRouter 被 Stripe 收购（传闻中） | OpenRouter 正与 Stripe 传闻约 $100 亿收购案（未确认，2026年8月），若成真，定价模型和 BYOK 策略可能全面重构 |
| 若某模型原厂降价 | 部分提供商有峰谷折扣（如 DeepSeek 50~75% 非峰时段折扣），若用 BYOK 在 OpenRouter 设置自有 Key，则按提供商折扣价计费。 中转站的对应价格不会自动更新 |
| 若中转站依赖逆向工程渠道被封 | 价格和可用性数据失真，需要心跳探活机制兜底 |
| 若 GenStudio 再次调整计费 | 无问芯穹历史上做过输入/输出 token 定价比例优化（输入降、输出升），并终止过部分临时折扣政策。 任何硬编码的采集逻辑都会失效 |

# 🔬 第二轮（收敛）：钢人论证后的残存论点

逐一拷问后，以下结论无法被推翻：

1. **不存在一个 API 能覆盖所有层**。必须分层：结构化 API + 半结构化 HTML 爬虫 + 运行时实测。
2. **"缓存命中率"不是可静态采集的字段，而是运行时验证的结果**。
3. **Coding Plan 的 quota 结构（5小时/周/月窗口类型）比月费更重要**，但几乎无法自动化采集，需要人工维护。
4. **中转站必须加"存活状态"和"风险层级"标签**，不能仅采集价格。
5. **价格的真实含义是"有效成本"，即 token 定价 × 实际用量模式 × 缓存收益率**，单看单价会误导决策。

```python
def calculate_effective_cost(
    model_id: str,
    daily_input_tokens: int,
    daily_output_tokens: int,
    cache_hit_rate: float = 0.0,   # 实测后填入，默认0
    days: int = 30,
    db=DB
):
    """
    真实成本公式：
    cost = (input_tokens × input_price
            + cached_tokens × cache_read_price
            + cache_write_tokens × cache_write_price
            + output_tokens × output_price)
           × calls_per_day × days
    """
    con = sqlite3.connect(db)
    cur = con.cursor()
    cur.execute("""SELECT input_price, output_price, cache_read_price,
                          cache_write_price, cache_discount, name
                   FROM provider_models
                   WHERE date=? AND model_id=?""", (TODAY, model_id))
    row = cur.fetchone()
    con.close()

    if not row:
        print(f"模型 {model_id} 今日无数据")
        return

    inp, out, cr, cw, disc, name = row
    # 缓存命中的 token 分布
    cached_tokens  = daily_input_tokens * cache_hit_rate
    uncached_tokens = daily_input_tokens * (1 - cache_hit_rate)

    daily_cost = (
        uncached_tokens * (inp or 0) / 1_000_000 +
        cached_tokens   * (cr  or inp or 0) / 1_000_000 +
        cached_tokens   * (cw  or 0) / 1_000_000 +   # 写入成本（首次缓存）
        daily_output_tokens * (out or 0) / 1_000_000
    ) * (1 - disc)

    monthly_cost = daily_cost * days

    print(f"\n📊 有效成本估算 | {name}")
    print(f"   日输入: {daily_input_tokens:,} tokens（缓存命中率 {cache_hit_rate*100:.0f}%）")
    print(f"   日输出: {daily_output_tokens:,} tokens")
    print(f"   日成本: ${daily_cost:.4f}")
    print(f"   月成本: ${monthly_cost:.2f}")
```

## Layer C：缓存命中率实测脚本

```python
# cache_hit_tester.py
"""
向目标平台发送2次相同前缀请求，检验 cached_tokens 是否出现在响应中。
这是验证"该中转站是否透传/支持缓存"的唯一可靠方法。
"""
import httpx, time

def test_cache_hit(base_url: str, api_key: str, model: str):
    SYSTEM = "你是一个专业的代码审查助手。" * 100  # 重复以产生足够长的可缓存前缀

    def call(question: str):
        r = httpx.post(f"{base_url}/v1/chat/completions",
            headers={"Authorization": f"Bearer {api_key}",
                     "Content-Type": "application/json"},
            json={
                "model": model,
                "messages": [
                    {"role": "system", "content": SYSTEM},
                    {"role": "user",   "content": question}
                ],
                "max_tokens": 10
            }, timeout=30)
        data = r.json()
        usage = data.get("usage", {})
        return {
            "cached_tokens":    usage.get("prompt_tokens_details", {}).get("cached_tokens", 0),
            "cache_discount":   data.get("cache_discount", None),  # OpenRouter 专有字段
            "prompt_tokens":    usage.get("prompt_tokens", 0),
        }

    print(f"\n🔬 缓存实测 | {base_url} | {model}")
    r1 = call("第一次调用，预热缓存")
    time.sleep(1)
    r2 = call("第二次调用，验证命中")

    print(f"  第1次 cached_tokens: {r1['cached_tokens']}  cache_discount: {r1['cache_discount']}")
    print(f"  第2次 cached_tokens: {r2['cached_tokens']}  cache_discount: {r2['cache_discount']}")
    hit_rate = r2['cached_tokens'] / r2['prompt_tokens'] if r2['prompt_tokens'] else 0
    print(f"  实测缓存命中率: {hit_rate*100:.1f}%")
    return hit_rate

# 使用示例
if __name__ == "__main__":
    # 测试 OpenRouter（应能看到 cache_discount 和 cached_tokens）
    test_cache_hit(
        base_url="https://openrouter.ai/api",
        api_key=os.environ["OPENROUTER_KEY"],
        model="anthropic/claude-sonnet-4-5"
```

# 1. What：客观事实/现象是什么？

## 1.1 “模型”本身已经不是一个完整产品对象

现在一个模型至少存在四种不同身份：

```text

    ↓
模型本体
    ↓
官方 API
    ↓
第三方 Inference Provider
    ↓
Gateway / Aggregator / Relay
    ↓
Coding Tool / IDE / Agent
```

例如同一个 Claude / GPT / Kimi / GLM：

```text

├── 官方 API
├── OpenRouter
├── 302.AI
├── AIHubMix
├── DeerAPI
├── 无问芯穹
├── SiliconFlow
├── DeepInfra
├── Novita
└── ...
```

这些渠道可能拥有完全不同的：

* 价格
* 上下文上限
* Cache 价格
* Cache TTL
* QPS
* Tool Calling
* Structured Output
* Files / Vision
* Responses API
* Anthropic Messages API
* 数据保留策略
* 路由策略
* 可用性

OpenRouter 当前模型 API 就明确把 `context_length`、`created`、`pricing`、`supported_parameters`、`top_provider` 等作为模型数据的一部分；而模型的 endpoint 又可以进一步展开到具体 provider。([OpenRouter][1])

```text

→ supported_parameters / pricing / context

OpenRouter endpoints
→ 同一模型进一步拆成 provider endpoint
→ provider-specific pricing / capabilities

结论：
“模型”不能直接等价于“使用方式”
```

## 1.3 “缓存命中率”不是“缓存价格”

这两个问题必须严格分开。

例如：

```text
Cache Read Price = $0.20 / 1M
```

只能说明：

> 如果命中缓存，读取这些 token 要多少钱。

它不能告诉你：

> **实际有多少输入 token 命中了缓存。**

OpenRouter 当前会在响应的 `prompt_tokens_details` 中直接给出：

```text
cached_tokens
cache_write_tokens
```

同时还可通过 `cache_discount` 观察缓存带来的成本变化。([OpenRouter][5])

因此至少有两个指标：

### Token Cache Hit Rate

```text
cached_input_tokens
÷
eligible_input_tokens
```

### Request Cache Hit Rate

```text
cache_hit_requests
÷
cache_eligible_requests
```

二者完全不同。

一个请求可能：

```text
10 万 input tokens
9 万 cached
```

那么：

```text
Token Hit Rate = 90%
```

但请求本身可能只算一个命中。

## 2.1 用户实际上是在寻找“可用方案”，不是寻找“模型”

最终用户的问题其实是：

这个时候真正比较的其实是：

```text
模型能力
+
工具适配
+
价格
+
配额
+
缓存
+
限频
+
稳定性
+
路由
```

而不是模型本身。

## 2.2 同一个模型，在不同渠道可能是不同的“实际产品”

例如 OpenRouter 明确存在：

> provider-specific endpoint

而且同一个模型的不同 Provider 可能有不同：

* context
* completion limit
* tool support
* price
* throughput
* latency。

> 同一个模型的 endpoint 支持能力可能不同。

([OpenRouter][10])

因此你的系统应该把：

```text

```

与：

```text

```

分离。

## 2.3 Coding Plan 甚至不能按 Token Price 简单换算

这点特别重要。

Claude Max 当前不是简单：

```text
$200 / 某数量 token
```

而是：

* weekly limit
* 模型不同导致消耗不同
* Claude 与 Claude Code 共享额度。([Claude帮助中心][11])

* weekly usage limit
* 不同模型对应不同估算请求量

例如当前官方文档直接给出了不同套餐在 5 小时窗口中的估算消息量。([OpenAI Help Center][12])

Kimi Code 也是：

* 5 小时滚动窗口
* 7 天额度
* 月额度
* CLI / VS Code / 第三方工具共享。([Kimi][9])

所以 Coding Plan 本质上是：

不是普通 Token API。

### 致命追问

> **既然最终都是 token，为什么不能统一换算成 token 后比较？**

### 正方钢人

确实可以做“近似经济价值”。

例如：

```text
套餐月费 ÷ 套餐内估计 token
```

```text
estimated $ / 1M tokens
```

这对于消费者非常有帮助。

### 反方钢人

但是：

```text
5 小时限制

并发限制
不同模型权重

隐藏的 MCP 消耗

```

都会破坏这个换算。

> Coding Plan 必须作为独立产品类型建模，不能被压平为 API Token Price。

# 3. Where / When：适用边界和时间节点是什么？

## 3.1 “每天采集一次”可以成立，但“今天新发布”必须有时间语义

至少要有：

```text
released_at
announced_at
published_at
listed_at
discovered_at
price_effective_at
```

例如模型可能：

```text
9/28 官方发布
9/28 Hugging Face 出现
9/29 OpenRouter 上线
9/30 302.AI 上线
```

那么：

```text
MODEL_RELEASED
MODEL_PUBLISHED
MODEL_API_AVAILABLE
MODEL_PROVIDER_ADDED
```

是四个不同事件。

OpenRouter 模型 API 直接暴露 `created`；Models.dev 当前源码数据同样包含 `created`、pricing、supported parameters 等字段。([OpenRouter][1])

---

## 3.2 每日一次应该做“快照 + diff”，而不是简单重新抓取

比如：

```text
2026-09-29 snapshot
2026-09-30 snapshot
```

比较：

```text
new_model
removed_model
new_provider
removed_provider
new_endpoint
price_up
price_down
cache_price_changed
context_changed
capability_changed
tool_compat_changed
plan_quota_changed
```

这比直接抓新闻稳得多。

---

## 3.3 时效性有两种

### 类型 A：实时变化

例如：

* 新模型
* 临时促销
* Provider 下线
* 价格调整

### 类型 B：稳定属性

例如：

* 厂商
* 参数规模
* context
* benchmark
* 模型定位

所以：

```text
实时市场数据
```

与：

```text
模型知识卡
```

不能完全相同频率维护。

---

### 致命追问

> **既然系统每天只跑一次，是否足够发现“今天发布的模型”？**

### 正方钢人

绝大多数情况下足够。

只要保存：

```text
official_release_at
source_fetched_at
```

每天跑一次就能发现“过去 24 小时发生什么”。

### 反方钢人

但是如果你把：

```text
今天上新
```

定义成：

> “北京时间今天零点以后官方发生的所有事件”

那么一次每日采集可能无法准确区分边界。

而且 AllAIModel 自己也明确写了：

> 每日更新，但数据可能滞后供应商公告。([Allai Model][13])

**幸存论点：**

> 每日采集足够做“每日情报”，但必须保存原始时间戳，不能让“采集时间”冒充“发布时间”。

# 6. What if：如果前提改变，结论会怎样？

这里是最容易把系统做死的地方。

## 情况 A：模型官方撤掉，但第三方仍然提供

不能简单：

```text model disappeared = deleted
```

应该：

```text official_status = deprecated
provider_availability = active
```

---

## 情况 B：模型名称不变，实际版本换了

比如：

```text model = xxx-latest
```

实际上后台发生：

```text v1
→ v2
```

因此需要：

```text model_alias
canonical_model
snapshot_model
```

三层关系。

---

## 情况 C：Provider 价格没变，但 Cache 价格变了

不能只检测：

```text input_price
output_price
```

必须：

```text input_price
cache_write_price
cache_read_price
output_price
storage_price
```

---

## 情况 D：Provider API 便宜，但 Coding Plan 更划算

这时不能直接按：

```text $/1M tokens
```

排。

需要提供：

```text API Cost
vs
Subscription Cost
vs
Observed Cost Per Completed Task
```

---

## 情况 E：协议兼容，但工具不兼容

例如：

```text OpenAI-compatible = true
```

但是：

```text Responses ❌
Tool Calls 部分支持
Structured Output ❌
```

那么：

```text Codex
```

和：

```text 普通 OpenAI SDK
```

得到的结果可能完全不同。

# 第二轮：收敛与苏格拉底拷问

下面把整个思路进行一次更强的反证。

---

## 拷问 1：到底是在做“模型数据库”还是“AI 服务市场数据库”？

### 质问

如果最终用户关心：

> “在哪里用？”

那是不是模型数据库已经不够？

### 一方

模型数据库是核心。

没有模型本体，就没有渠道关系。

### 另一方

但是：

```text
Claude
```

本身只是一个模型家族。

用户真正需要：

```text
Claude
→ Anthropic
→ OpenRouter
→ 302.AI
→ Cursor
→ Claude Code
```

所以真正的产品实体应该是：

> **Model Intelligence + Access Intelligence**

### 结论

应该是：

```text
AI Model Intelligence Platform
```

而不是：

```text AI Model Catalog
```

---

# 拷问 2：模型“效果如何”到底是谁说了算？

### 一方

直接使用：

* Benchmark
* Artificial Analysis
* LMSYS 等评测

### 另一方

Benchmark 不等于真实生产效果。

一个模型可能：

```text SWE-bench 强
但工具调用差
```

或者：

```text 数学强
但中文写作一般
```

所以必须区分：

```text Benchmark Evidence
Vendor Claim
Independent Evaluation
Observed Evaluation
```

例如 OpenRouter 自己都强调 benchmark / intelligence 排序，同时模型页面又要求查看实际 provider 的 endpoint 限制与支持参数。([OpenRouter][1])

### 结论

最终不要只给：

> “评分 94 分。”

而应给：

```text
编码       ：强
长上下文   ：强
工具调用   ：中/强
中文       ：强
视觉       ：支持
Agent      ：强

证据：
Benchmark
官方声明
独立评测
你的实测
```

---

# 拷问 3：缓存命中率能不能直接从供应商网站采集？

### 一方

如果 API 返回：

```text cached_tokens
```

当然可以。

### 另一方

很多 Provider 只提供：

```text cache read price
```

不会公开：

```text 实际 cache hit %
```

即使提供，也可能是平台总体数据，不是你的账户。

所以：

> **公共缓存价格 ≠ 你的缓存命中率。**

OpenRouter 明确提供了 `cached_tokens` 与 `cache_write_tokens` 这样的响应级指标，这证明“实测缓存命中”可以计算；但如果某服务没有类似遥测，你就不能凭价格页推导出命中率。([OpenRouter][5])

### 结论

必须建立：

```text Provider Advertised Cache
+
Own Observed Cache
```

两个体系。

---

# 拷问 4：Coding Plan 的“额度”能不能每天自动抓？

### 一方

完全可以抓官网。

### 另一方

部分 Coding Plan 的关键数据只在：

```text 登录后控制台
```

展示。

无问芯穹就明确说明具体 RPM/TPM/RPD 要到控制台查看；它没有公开固定数值。([Infini AI 文档][19])

Kimi 则提供登录后的额度和限频状态查询。([Kimi][9])

因此：

```text public data
+
authenticated account data
```

应该是两条路径。

### 结论

系统必须支持：

```text PUBLIC
ACCOUNT_AUTHENTICATED
OBSERVED
```

三个证据等级。

---

# 拷问 5：是否应该把 302.AI、OpenRouter、DeerAPI、无问芯穹放在同一张表？

### 一方

用户就是想比较：

> “在哪里调用这个模型最方便？”

放一起非常合理。

### 另一方

它们的商业模式完全不同：

```text OpenRouter
= 聚合 + Provider routing

302.AI
= 多模型统一 API / Gateway

无问芯穹
= MaaS / 企业级模型服务

DeerAPI
= Unified API Gateway

Anthropic
= 官方模型/API

Cursor
= Coding Tool + Subscription + Model Access
```

如果不记录角色，用户会误以为：

> “OpenRouter 和 Anthropic 是同一种企业。”

### 结论

UI 可以放一起比较。

数据库一定要保留：

```text channel_type
```

## 例如 OpenRouter

当前官方 Prompt Caching 文档明确支持：

```text
cached_tokens
cache_write_tokens
cache_discount
```

并且还有：

> Provider Sticky Routing

通过把后续请求固定到相同 provider 来提高 cache hits。([OpenRouter][5])

甚至 OpenRouter 自己还有另一套：

> Response Caching

它与 provider prompt caching 是两套不同机制。官方文档明确说明：

```text
OpenRouter Response Cache
≠
Provider Prompt Cache
```

而且 response cache 命中不计 provider rate limit。([OpenRouter][25])

因此你的数据库甚至应该区分：

```text
provider_prompt_cache
gateway_response_cache
```

这是非常关键的架构细节。

# 七、最后的幸存结论

经过上面的反证，我认为以下几点基本成立。

### 第一

你最开始的：

> “每天采集今天新出了哪些大模型”

只是系统的**入口需求**。

真正产品应该是：

> **每天更新 AI 模型 + Provider + Gateway + Pricing + Plan + Tool + Cache + Reliability 的市场状态。**

---

### 第二

必须把：

```text
Model
Provider
Gateway
Tool
Plan
```

拆开。

否则一旦遇到：

```text
Claude + Anthropic
Claude + OpenRouter
Claude + 302
Claude + Cursor
Claude + Claude Max
```

数据库马上混乱。

---

### 第三

“模型效果”必须和“在哪里使用”分离。

一个模型的能力可以是：

```text
★★★★★ Coding
```

但某个具体 endpoint：

```text
Tools = ❌
Context = 256K
```

那么用户用它跑 Agent 的结果可能完全不同。

---

### 第四

“价格”必须至少做到：

```text
Input
Cached Input
Cache Write
Output
Batch
Priority/Flex
Image
Audio
Video
Search
```

并记录：

```text
官方价格
渠道价格
促销价格
观察价格
```

---

### 第五

“Coding Plan”不能压缩成价格。

必须记录：

```text
5h
Daily
7d
Weekly
Monthly
Credits
Tokens
Requests
Concurrency
Tool quota
Overage
Reset rule
```

而且 **Kimi / Claude / OpenAI / GLM / MiniMax 当前已经证明这些计量方式并不统一**。([Claude帮助中心][11])

---

### 第六

“缓存命中率”不能靠价格页推测。

必须分成：

```text
Advertised Cache
+
Observed Cache
```

后者只有通过 API usage / gateway telemetry / 自己的探针才能得到。OpenRouter 当前已经提供 `cached_tokens`、`cache_write_tokens`、`cache_discount`，因此可以直接证明这条技术路线是可行的。([OpenRouter][5])

---

### 第七

你真正应该每天生成的不是：

> “今日 AI 新闻”

而应该是：

# 《AI 每日市场快照》

例如：

```text
2026-09-30

一、今日新模型
  ├─ Model A
  ├─ Model B
  └─ Model C

二、今日新增 Provider
  ├─ Provider X
  └─ Provider Y

三、今日新增中转/Gateway
  ├─ Gateway A
  └─ Gateway B

四、今日价格变化
  ├─ Model A ↓ 30%
  └─ Model B ↑ 20%

五、今日 Coding Plan 变化
  ├─ Kimi
  ├─ GLM
  ├─ Claude
  └─ Codex

六、今日 Cache 变化
  ├─ Provider A 新增 1h cache
  └─ Provider B Cache Read 降价

七、今日工具兼容性变化
  ├─ 新增 Claude Code
  ├─ 新增 Codex
  └─ 新增 OpenCode

八、今日值得关注模型
  ├─ 编程
  ├─ 推理
  ├─ Agent
  ├─ 视觉
  └─ 视频

九、可直接使用渠道矩阵
  Model × Provider × Price × Protocol × Tool

十、证据链
  每条记录 → Source → fetched_at → snapshot
```

这才真正解决你描述的用户需求。
